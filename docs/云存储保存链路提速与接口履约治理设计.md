## 0. 背景与问题定位

### 0.1 实测日志拆解（华为云盘，11.8MB 库，save total 13463ms）

| 阶段 | 耗时 | 内容 |
|---|---|---|
| 守卫 + 客户端#1 + 刷新令牌#1 | ~0.6s | `DatabaseLoadGuard.checkBeforeRead` 新建 manager → 新建 client → token POST |
| 路径逐级下钻 | ~2.4s | list(root)+getInfo(root)+3×list——Worker 内路径缓存水合失败，静态缓存冷启动 |
| 客户端#2 + 刷新#2 + getInfo×2 | ~0.25s | `readToFile` 再建 manager；`downloadRangeToFile` 内部又 getInfo 取 size（findFileByPath 已返回过） |
| 下载 11.8MB（顺序 2 块） | 6.7s | ~1.8MB/s 串行 Range GET |
| sha256 / build(buffer) | 0.09s / 0.61s | v3/AES 库走整缓冲回退（mode=buffer） |
| 客户端#3 + 刷新#3 + getInfo | ~0.15s | `writeSavedContent` 再建 manager |
| 上传 PATCH | 2.73s | axios 整缓冲 |
| 客户端#4 + 刷新#4 + getInfo | ~0.26s | `postSuccess` 再建 manager 再 getInfo |

一次保存 = **12 个 HTTP 请求 + 4 次 token 刷新 + 4 次 axios 实例重建**，编排开销约 3.7s（27%）。

### 0.3 契约事实（已核实）

- `IFileStorage.ets:86-93` `WriteOption.expectedVersion`：*不支持原生条件写的存储应在写入前重新获取版本比对，不一致抛 VERSION_CONFLICT*。Local/FTP/WebDAV/OneDrive/pCloud/S3 均已履约，**华为是唯一忽略该参数的云存储**。
- `IFileStorage.ets:130-134` `FileInfo.version`：*存储原生版本标识（不透明字符串），无此能力的存储返回 null，由上层用内容哈希兜底*。华为返回 null 属未履约（返回本身不违约，但导致基线 A 永不生效）。
- 版本指纹先例：Local/FTP `size|mtime`（`LocalFileStorage.ets:297`、`FTPStorage.ets:392`）、WebDAV/OneDrive `buildVersion(etag, lastModified)`、pCloud `buildVersion(meta)` 复合指纹、S3 etag。

## 1. 目标与非目标

**目标**
1. 华为云盘无冲突保存 13.4s → ~3.5-4s；请求数 12+4 刷新 → 2-3+0-1 刷新。
2. 所有修复遵守分层原则：**编排层零 provider 分支，provider 逻辑全部在具体实现类**。
3. 华为云盘补齐 version/条件写契约履约。
4. OneDrive/pCloud 等同类问题一并修复；加载流程同步受益。

**非目标**
- 不改 KDBX 格式与 S6 流式管道行为（mode=buffer 回退是 v3/AES 库的正常路径）。
- 不动 OneDrive readToFile 整缓冲现状（S7 遗留调研项，内存问题非本期能耗问题）。
- FTP/Local 不开启版本快速路径（mtime 粒度风险 / 无网络收益）。

## 2. 分层归属原则

| 层 | 允许的改动 | 本方案改动 |
|---|---|---|
| 编排层 `workers/DatabaseSave`、`DatabaseLoad`、`DatabaseLoadGuard` | 只依赖 IFileStorage 契约的通用流程控制，零 provider 分支 | WP1/WP2 |
| 接口层 `IFileStorage` | 仅在确有必要时扩展契约 | WP3（可选能力成员） |
| 实现层 各 Storage/Client | 补齐契约 + 纯内部优化 | WP4/WP6 |
| 共享服务层 `OAuth2TokenStorageService`、`HuaweiDrivePathCacheStore` | Worker 环境适配 | WP5 |

## 3. 工作包设计

### WP1 编排层：单 manager 贯穿一次保存/加载（全存储受益，无契约变化）

1. `handleSaveDatabase`/`loadKdbxFileToFile` 顶部创建一个 `KdbxFileManager`，贯穿守卫/下载/写入/postSuccess；MERGE 重试循环内复用（刷新结果随 config 原地更新，天然传递）。
2. `DatabaseLoadGuard.checkBeforeRead` 改为接收传入 manager，**返回守卫内部 `getInfo` 的 FileInfo**（目前被丢弃），免费充当 WP2 预检。
3. `writeSavedContent` 返回 `writeFromFile` 的 FileInfo，`postSuccess` 直接消费；删除 postSuccess 的 manager+getInfo。回退整缓冲路径由 `getInfo` 补齐（`write` 契约无返回值）。

### WP2 编排层：版本预检快速路径（通用逻辑，能力开关控制）

```
fileInfo = 守卫返回的 getInfo 结果          // 0 额外请求
if (expectedVersion !== null
    && fileInfo.version === expectedVersion
    && storage.supportsVersionFastPath?.() === true):
    跳过 readToFile + sha256 → build → 带 expectedVersion 条件写
else:
    现有全量下载 + 双基线路径（行为不变）
```

- 安全闭环：条件写（写前复核）在 PATCH 前再取一次最新版本，预检与写入之间远端被改 → VERSION_CONFLICT → 现有冲突分支。
- 残余风险（同 size 同 mtime 的远端并发修改穿透两道校验）在本文档声明：KDBX 每次写入 IV/nonce 变化导致 size 变动，实际概率极低。
- MERGE 重试（Q8）改为仅重跑预检，不再整轮守卫+全量下载。

### WP3 接口层：版本可信度能力声明（唯一接口改动）

`IFileStorage` 新增可选能力成员 `supportsVersionFastPath?(): boolean`（未实现视为 false），各实现自行 opt-in，编排层只读开关。纠正 S7 遗留的 `VERSION_FAST_PATH_TYPES` 白名单思路（storageType 硬编码在上层违反面向接口原则）。

| 存储 | opt-in | 依据 |
|---|---|---|
| S3 | 首批 | etag 服务端原子 |
| 华为云盘 | 首批（随 WP4 补齐+真机验证） | id:size:editedTime 复合指纹 |
| WebDAV/OneDrive/pCloud | 验证后 | etag/复合指纹已有 |
| Local/FTP | 否 | 无网络收益 / mtime 粒度风险 |

### WP4 实现层：华为云盘补齐契约 + 内部优化（全部在 HuaweiDriveStorage/Client 内）

| 项 | 内容 | 位置 |
|---|---|---|
| 4a 履约 version | 静态 `buildVersion(file)` = `id:size:editedTime`，`getInfo/readToFile/writeFromFile/listDir` 统一透出 | HuaweiDriveStorage |
| 4b 履约条件写 | `write`/`writeFromFile` 在 findFileByPath 结果上比对版本，不一致抛 VERSION_CONFLICT；远端不存在放行（对齐 OneDrive fail-open） | HuaweiDriveStorage |
| 4c 去冗余请求 | `downloadRangeToFile` 增 size 参数删除内部 getInfo；`writeFromFile` 尾部 getInfo 改为解析 PATCH `fields=*` 响应体 | HuaweiDriveClient/Storage |
| 4d 路径缓存 Worker 化 | `HuaweiDrivePathCacheStore` 从 preferences 改 filesDir JSON 文件（`CommonUtils.getAppFilesDir()`，§11.1 已注入）；水合/防抖逻辑不动 | HuaweiDrivePathCacheStore |
| 4e 下载提速 | 串行 8MB → 2-4 路并发 Range GET（按偏移 fs.write）；冲突校验场景提速 | HuaweiDriveClient |

### WP5 共享服务层：OAuth2 令牌持久化 Worker 化（OneDrive + 华为同修）

- **方案 A（落地）**：`OAuth2TokenStorageService` 持久化后端改为 filesDir 加密 JSON 文件（复用 `CryptoUtils.encryptText`；Worker 内经注入路径可用，不依赖 Context/preferences）。
- 修复 Q9：`init` 改为可 await 的幂等单飞（`opening` Promise 去重），所有公开方法先 `await this.ensureInit()`。
- OneDrive 补刷新单飞（镜像华为 `refreshingPromise` 模式）。
- 备选 B（若 A 受阻）：Worker 成功消息回传 token，主线程持久化。不采用，除非 A 验证失败。

### WP6 实现层：其他存储同类问题审计清单

| 存储 | 问题 | 处置 |
|---|---|---|
| OneDrive | writeFromFile 尾部 getInfo 冗余；无刷新单飞；token 持久化失败 | 尾部 getInfo 保留（upload session 末分片响应解析收益小、改动大，暂不动）；单飞补齐；WP5 覆盖 |
| pCloud | 写前按目录列表定位复核 | 保留（pCloud API 无单文件 stat 端点时的既有设计，列表已带 hash 可复用），本期不动 |
| S3 | 尾部 HEAD 较轻；Range 下载串行 | 不动；快速路径首批开启 |
| WebDAV | 已达标 | 仅 opt-in |

## 4. 实施顺序

1. **WP1**（纯编排，先落地立减 ~1s + 3 次重建）
2. **WP5 + WP4d**（去 2.4s 下钻 + 跨操作刷新）

每步独立可交付：存储回归 12 套件 + UI 2 套件 + hilog 阶段打点前后对比。

## 5. 验收标准

1. **功能**：存储回归 12 套件 + UI 2 套件全绿；S3/华为快速路径与全量路径行为等价（无冲突保存、冲突触发 AUTO/MERGE、OVERWRITE 语义不变）。
2. **性能（华为真机，11.8MB 库）**：无冲突保存 ≤ 4.5s；单次保存 token 刷新 ≤ 1 次（token 有效时 0 次）；HTTP 请求 ≤ 4。
3. **契约**：华为 `getInfo/readToFile/writeFromFile` 均透出 version；`write/writeFromFile` 传入 expectedVersion 且远端已变时抛 VERSION_CONFLICT；远端不存在时放行。
4. **Worker 适配**：Worker 内路径缓存可水合/落盘（日志无 "context is invalid"）；token 刷新后落盘，重启后无需再刷（token 有效期内）。
5. **可观测**：快速路径命中/未命中在 hilog 打点可见（`save fast-path: hit/miss(version mismatch|no capability)`）。
