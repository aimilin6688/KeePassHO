## 1. 背景

KeePassHO 的数据库文件（KDBX）存放在多种远端存储（WebDAV / S3 / OneDrive / 华为云盘 / pCloud / FTP / SFTP / 本地），天然存在**多设备并发编辑**场景：手机 A 与手机 B 同时打开同一数据库，各自修改后先后保存。KDBX 是单文件整体加密格式，后写者若不感知先写者，将直接**覆盖掉先写者的修改**（静默丢数据）。

当前代码已具备基础的"修改时间不一致则合并"逻辑，但存在竞态窗口、基线不可靠、远端改密即失败等缺陷。本方案在**不改变现有同步/Worker 双执行模式**的前提下，从接口层、编排层、数据安全层三个层面系统性解决。

### 1.1 现有架构：同步模式与 Worker 模式

加载与保存各有两种执行模式，由编译期常量切换，**当前均为同步模式**（`Constants.ets:5,9` 中 `ASYNC_SAVE_DATABASE = false`、`ASYNC_LOAD_DATABASE = false`）：

```
UI 层（DatabaseView / EntryView / ChangePassword / 设置页…）
  │  统一入口：KdbxUtils.saveDatabase(callback)          (KdbxUtils.ets:578)
  ▼
KdbxSaveService.saveDatabase(callback)                    (KdbxSaveService.ets:28)
  │  从 FileService 单例取 DbFileParam（内存态：database、modifiedTime、凭证、存储配置）
  │  构造 SaveDatabaseMessage(dbFileParam.database, dbFileParam)
  ├─ 同步模式（当前）：new DatabaseSave(callbackWarp).handleSaveDatabase(req)
  │     · 在调用线程（主线程）直接执行
  │     · request.data 就是 Kdbx 对象本身（同一引用，无需序列化）
  │     · 回调直接函数调用
  └─ Worker 模式：KdbxSaveService.saveDatabaseAsync(req, callback)
        · 先 kdbxToArrayBuffer(database)：kdbx.saveSnapshot() 序列化为 KPSN 二进制快照 ArrayBuffer（2026-10 前为 saveXml XML）
        · new worker.ThreadWorker('entry/ets/workers/DatabaseSaveWorker.ets')
        · postMessage(req, [buffer])  // transfer list 零拷贝转移
        · Worker 端 DatabaseSaveWorker extends DatabaseSave，覆写
          postMessage/postErrorMessage/postSuccessMessage → workerPort.postMessage
        · 每次保存前 terminate 旧 Worker 再重建（无复用）
```

加载侧完全对称（`KdbxLoadService.ets:20-24` → `DatabaseLoad.ets`）。

**设计要点：两种模式共享同一套核心业务类**（`DatabaseSave` / `DatabaseLoad`），差异全部收敛在三个 `postXxx` 通信方法上（模板方法模式）；Worker 边界上 `request.data` 从 `Kdbx` 变为 KPSN 快照 ArrayBuffer，由 `KdbxUtils.arrayBufferToKdbx()` 在核心逻辑内部透明还原（`instanceof Kdbx` + `'KPSN'` 魔数分发，KdbxUtils.ets:327-345）。

**对本次设计的约束**：所有新增字段必须能通过 `JSON.stringify` 跨 Worker 边界（参考 `SaveDatabaseMessage` 构造函数中手工列举字段的做法，`DatabaseSaveWorkerParam.ets:19-31`）；所有新增逻辑必须写在 `DatabaseSave`/`DatabaseLoad` 这层共享代码里，保证两种模式行为一致。

### 1.2 现有冲突处理流程

`DatabaseSave.handleSaveDatabase`（`DatabaseSave.ets:28-50`）：

1. 重读远端文件 `loadKdbxFileContent()` → `FileContentInfo(content, modifiedTime)`
2. **单一 mtime 比较**：`fileContent.modifiedTime !== request.modifiedTime`（DatabaseSave.ets:38）
   - 不一致 → `mergeDatabase()`：`Kdbx.load(远端内容)` → `arrayBufferToKdbx(本地内容)` → `oldKdbx.merge(newKdbx)` → 保存合并结果
   - 一致 → 直接保存
3. 保存：`database.save()` → `kdbxFileManager.write()`（无条件 PUT/上传）→ `getInfo()` 取新 mtime → `SuccessMessage(content, modifiedTime, isMerge)`
4. 成功回写：`KdbxSaveService.handleSuccess` 更新 `dbFileParam.modifiedTime`；若发生合并，把合并结果重新解析回 `dbFileParam.database` 并广播 `EventBus.DATABASE_RELOAD`，否则广播 `DATABASE_UPDATE`

### 1.3 现状缺陷

| # | 缺陷 | 位置 | 说明 |
|---|------|------|------|
| D1 | mtime 单一基线，可靠性不足 | DatabaseSave.ets:38 | WebDAV `Last-Modified` 仅秒级精度，两次保存落在同一秒则检测不到变更；部分服务器 mtime 行为不可靠。`WebDavClient` 已解析 `getetag`（WebDavClient.ets:545）但 `WebDAVStorage.getInfo()` 直接丢弃 |
| D2 | TOCTOU 竞态窗口 | DatabaseSave.ets:35-44 | "读远端→比较 mtime→PUT" 不是原子操作。A、B 同时检测到无变更后先后 PUT，后写覆盖先写，合并逻辑完全失效 |
| D3 | 远端改密导致保存整体失败 | DatabaseSave.ets:80 | `mergeDatabase` 中 `Kdbx.load(远端)` 用本地凭证，若远端已被他人改密则抛 `InvalidKey`，整个保存失败，本地修改被卡死（只能另存导出） |
| D4 | editState 墓碑未启用 | kdbx.ts:462-479 | kdbxweb 移植库已实现 `getLocalEditState`/`setLocalEditState`/`removeLocalEditState`（为合并提供 per-entry 修改痕迹），当前调用链完全未使用，削弱合并精度 |
| D5 | 冲突无重试上限/无退避 | DatabaseSave.ets | 合并后直接写回，若对端高频写入（如另一设备开着自动保存），理论上存在反复冲突 |

## 2. 开源实现调研结论

对 KeePass 生态四个主流实现做了源码调研（仓库快照见 `/var/folders/4n/mmg0d9wn1hj0m7dh2qnlb_f80000gp/T/deveco/research/`）：

| 维度 | keeweb (JS) | KeePassXC (C++) | keepass2android (C#) | KeePassDX (Kotlin) |
|------|-------------|-----------------|----------------------|--------------------|
| 版本标识 | 不透明 `rev` 字符串（存储自定义：WebDAV=Last-Modified / SHA256 前缀，OneDrive=eTag） | 内容 hash（前 1KiB MD5） | `CheckForFileChangeFast` 返回不透明串，**允许返回 null 走全量下载** | mtime+size 快照 |
| 条件写 | `save(path, opts, data, cb, rev)` 单方法 + `{revConflict:true}` 错误；OneDrive 用 If-Match | 无（写前检测） | 无（写前检测） | 无 |
| WebDAV 写安全 | PUT 到 `.tmp` → 再 PROPFIND 复核期间无变化 → MOVE 原子替换（**不信任弱 ETag**） | — | 全量下载 SHA256 比较 | — |
| 内容终判 | `webdavStatReload` 选项：重新下载算 SHA256 前缀 | 前 1KiB MD5 | WebDAV/FTP 全量下载 + SHA256 | — |
| 合并语义 | kdbxweb 2-way merge + **editState 墓碑持久化** + 推送成功后清除 | 2-way merge（UUID+时间戳+History 隐式 base） | kdbxweb merge，CachingFileStorage 缓存层 | 2-way merge |
| 远端改密 | `remote-key-changed` 事件 → 引导输入新密钥 | 提示重开 | 提示重开 | 提示重开 |
| 活锁防护 | 冲突后重试上限 3 次 | — | — | — |

**采纳的关键结论**：
1. 条件写采用 **keeweb 单方法签名**（可选版本参数 + 冲突错误），而非双方法（`writeIfMatch` + `supportsConditionalWrite`），接口面更小，降级路径自然（不传参数即现状）。
2. WebDAV 的 ETag 分强弱（`W/"..."`），**不可作为唯一依据**；keeweb 的 "tmp+复核+MOVE" 是工程上最稳妥的伪条件写。
3. kp2a 证明：**版本串允许为 null**，此时编排层用"重新下载 + 内容哈希"兜底，是标准做法 → 本方案的**双基线**由此而来。
4. keeweb 的 `rev` 是**不透明字符串**，由各存储实现自定义语义，编排层只做相等比较 → `FileInfo.version` 由此而来。
5. KDBX 每次保存整体重加密，**块级增量无意义**，方案只做"整文件跳过/覆盖/合并"决策，不做 delta 传输。

## 3. 目标与非目标

### 目标
- G1 消除 TOCTOU：写入时能感知"基线之后远端已被他人修改"，拒绝覆盖并触发合并重试
- G2 提升变更检测可靠性：存储原生版本标识优先，内容哈希兜底
- G3 远端改密不再导致保存卡死：识别并引导用户输入新凭证完成合并
- G4 启用 editState 墓碑，提升跨保存回合的合并精度
- G5 方案落在 IFileStorage 接口层 + 编排层，8 个存储实现各自映射原生能力，互不感知
- G6 同步模式与 Worker 模式行为完全一致，新增字段可跨 Worker 序列化

### 非目标
- N1 不做块级/增量传输（KDBX 整体重加密，无收益）
- N2 不做离线队列/后台自动同步（保存仍由用户操作触发；自动重连上传是后续独立特性）
- N3 不做 3-way merge 的显式 base 文件管理（沿用 kdbxweb 隐式 base：UUID + 时间戳 + Entry History）
- N4 不改变现有双执行模式的开关与调度策略

## 4. 总体方案：三层架构

```
┌─────────────────────────────────────────────────────────────┐
│ L3 数据安全层                                                 │
│   Entry History（已有） · editState 墓碑（新启用） · 安全备份（可选）│
├─────────────────────────────────────────────────────────────┤
│ L2 编排层  DatabaseSave / DatabaseLoad（双模式共享）           │
│   双基线判定 → 条件写 → VERSION_CONFLICT → 重新读+合并 → 有界重试 │
│   远端改密识别 → 新凭证引导                                     │
├─────────────────────────────────────────────────────────────┤
│ L1 接口层  IFileStorage（8 实现 + Cache）                      │
│   FileInfo.version（不透明字符串）                              │
│   write(path, content, option?: {expectedVersion}) → StorageError(VERSION_CONFLICT) │
└─────────────────────────────────────────────────────────────┘
```

核心思想：**接口层只提供"能力"与"事实"（版本串、条件写失败信号），编排层负责"决策"（跳过/覆盖/合并/重试/报错）**。存储实现间的差异（ETag 强弱、有无 If-Match、MOVE 是否原子）全部封装在各自实现内，对编排层暴露统一的"不透明 version 串 + 冲突异常"契约。

## 5. 接口层详细设计（L1）

### 5.1 FileInfo 增加 version 字段

```ts
// IFileStorage.ets
export interface FileInfo {
  name: string;
  size: number;
  modifiedTime: number;
  path: string;
  type: FileType;
  childrenCount: number;
  /**
   * 存储原生版本标识（不透明字符串，仅用于相等比较）。
   * 语义由各存储实现自定义（ETag / lastModified / hash / 复合串）。
   * 无原生能力时可返回 null，编排层将走内容哈希兜底。
   */
  version: string | null;
}
```

同步修改 `FileInfoImpl`、`FileContentInfo`（构造函数从 fileInfo 复制 version；`fileInfo` getter 回填）。

**不变式**：
- `version` 仅做 `===` 比较，编排层与上层**永不解析其内容**
- 同一内容两次 `getInfo` 应返回相同 version（弱 ETag 服务器上以 `lastModified` 优先拼入）
- `version === null` 表示"该存储无法提供版本事实"，是合法值

### 5.2 write 签名扩展（keeweb 式单方法）

```ts
// IFileStorage.ets
export interface WriteOption {
  /**
   * 期望的远端当前版本（通常来自上次 read/getInfo 的 FileInfo.version）。
   * - 传入且存储支持条件写：仅在远端版本仍等于该值时写入，
   *   否则抛 StorageError(VERSION_CONFLICT)
   * - 传入但存储不支持原生条件写：实现应采用"写前复核"（见 5.4 兜底行），
   *   或在最坏情况下直接写入并返回（由编排层的双基线保证正确性）
   * - 不传（undefined）：无条件写入，与现有行为完全一致
   */
  expectedVersion?: string | null;
}

write(path: string, content: ArrayBuffer, option?: WriteOption): Promise<void>;
```

**兼容性**：`option` 为可选参数，现有全部调用点（导入导出、密钥文件读取、模板、缓存预热等）无需修改，编译期向后兼容。

### 5.3 错误码扩展

```ts
// StorageError.ets
export enum StorageErrorCodes {
  // …现有 7 项保持不变…
  /**
   * 条件写入失败：远端版本与 expectedVersion 不一致（已被其他设备修改）
   */
  VERSION_CONFLICT = 'VERSION_CONFLICT',
}
```

`StorageError` 结构不变（code + message），编排层用 `error instanceof StorageError && error.code === StorageErrorCodes.VERSION_CONFLICT` 判定。

### 5.4 各存储实现映射表

| 存储 | `version` 来源 | 条件写实现 | 实现要点 |
|------|---------------|-----------|---------|
| **WebDAV** | `PROPFIND` 的 `getetag` + `getlastmodified` 复合：`` `${etag}\|${lastModified}` ``（ETag 缺失/弱 ETag 时以 lastModified 为主） | **tmp + 复核 + MOVE**（keeweb 模式）：① `PUT path.tmp` ② `PROPFIND path` 复核 version 仍等于 expected ③ 相等则 `MOVE tmp → path`（OVERWRITE=T）；不等则删 tmp 并抛 `VERSION_CONFLICT` | `WebDavClient.ets:545` 已解析 etag，补 `getInfo` 透出即可；MOVE 前复核把 TOCTOU 收敛到"MOVE 原子性"，绝大多数服务器满足；不支持 MOVE 的服务器降级为"复核后直接 PUT" |
| **S3** | `ETag`（开启 bucket versioning 时拼 `versionId`：`` `${etag}\|${versionId}` ``） | `If-Match: <etag>`（S3 原生支持；versioning 桶用 `If-Match` + versionId 语义） | 412 Precondition Failed → `VERSION_CONFLICT` |
| **OneDrive** | `eTag`（Graph API `file` 资源原生字段） | `PUT` 请求头 `If-Match: <eTag>` | 412 → `VERSION_CONFLICT` |
| **华为云盘** | `etag`（Drive 对象字段） | 更新接口的 `If-Match` 头 | 同上 |
| **pCloud** | `hash`（文件内容 SHA1，list/download 元数据自带） | pCloud 无 If-Match：写前 `stat` 取 hash 与 expectedVersion 比较，相等才调用 `file-modify/upload` | 复核+写的窗口由 L2 重试兜底 |
| **FTP / SFTP** | `MDTM`+`SIZE` 复合：`` `${size}\|${mtime}` ``（SFTP 用 stat；FTP 优先 MLST，无 MLST 用 SIZE+MDTM） | 无原生能力：写前 `stat` 复核（同 pCloud 模式）；FTP 服务器时间精度常为秒，**version 大概率不可靠 → 返回值如实拼装，L2 的内容哈希终判兜底** | `@ohos/basic-ftp` / `sftp-ohos` 现有 API 能力内实现 |
| **Local（含沙箱/分享路径）** | `` `${size}\|${mtimeMs}` ``（fs.stat） | 无原生条件写：写前 stat 复核；本地单设备场景冲突概率极低 | — |
| **CacheStorage** | 透传底层存储 version | 透传 expectedVersion 给底层 | 缓存一致性规则不变 |

> 所有"写前复核"型实现（pCloud/FTP/SFTP/Local）共享同一个小工具函数（建议放 `storage/` 下 `VersionGuard.ets` 或抽基类静态方法）：`statVersion(path)` → 与 expected 比较 → 相等执行写入回调，不等抛 `VERSION_CONFLICT`。

### 5.5 渐进式实施策略

`version` 默认 `null`，各存储逐个点亮；编排层对 `null` 的处理见 6.2 —— **任何一个存储未改造，方案仍完整可用**（退化为"内容哈希终判 + 无条件写 + 重试"）。

## 6. 编排层详细设计（L2）

改造集中在 `DatabaseSave` / `DatabaseLoad`（双模式共享），`KdbxSaveService`/`KdbxLoadService` 的模式分支不动。

### 6.1 保存流程状态机（新版 handleSaveDatabase）

```
                    ┌──────────────────────────────────────────────┐
                    │ 0. 参数装配：request 携带 expectedVersion、     │
                    │    baseContentHash（来自 DbFileParam，见 6.5）  │

        │    （含 3b 写回时的冲突）                    retryCount++ ≤ 3 ?              │
        │                                             ├─ 是 ── 回到 1（带新基线）      │
        │                                             └─ 否 ──► 5. 冲突未决失败       │
```

与现状的关键差异：
- 步骤 2 的判定从"mtime 不等"升级为**双基线**（6.2）
- 步骤 3a/3b 的写入从无条件 PUT 升级为**条件写**
- 新增**步骤 4 有界重试**（上限 3，keeweb 同款），防止对端高频写入导致活锁
- merge 子流程捕获 `InvalidKey`（6.3）

### 6.2 双基线判定

```
基线A（快速路径）：request.expectedVersion（DbFileParam 记录的 version 串）
基线B（最终裁判）：request.baseContentHash（上次加载/保存成功时远端内容的 SHA256）

判定远端是否变化：
  changed = (expectedVersion != null && remoteVersion != null && expectedVersion !== remoteVersion)
         || (remoteContentHash !== baseContentHash)     // 内容级，永远执行
```

规则：
1. **两个基线都相等** → 远端未变，走 3a 快速路径
2. **任一不等** → 远端已变，走 3b 合并
3. `expectedVersion` 或 `remoteVersion` 为 null（存储未改造/无能力）→ 仅靠基线 B
4. **基线 B 永远计算**：`remoteHash = SHA256(remoteContent)`。代价是每次保存多读一次远端全量 + 哈希 —— 这与现状一致（现状本来就重读远端），只多了一次哈希计算（毫秒级）
5. KDBX 内含随机 IV/盐，**不同设备保存相同逻辑内容也会产生不同字节**，因此基线 B 只能判断"变没变"，不能判断"改了什么" —— 改了什么永远交给 kdbxweb merge（按 UUID + 时间戳 + History），这正是本方案不做 base 文件管理（N3）的原因

哈希实现：`@kit.CryptoArchitectureKit` `cryptoFramework.createMd('SHA256')`，在 `DatabaseSave` 内完成（Worker/同步模式均在非 UI 关键路径；同步模式在主线程，但一次 SHA256 远小于已有的解密+merge 成本）。

### 6.3 冲突合并子流程

```
mergeAndSave(request, remoteContent, remoteVersion, credentials):
  1. remoteKdbx = Kdbx.load(remoteContent, credentials)
     └─ 抛 KdbxError(InvalidKey) ──► 转 StorageError(REMOTE_KEY_CHANGED 概念，
        见 6.6 错误映射) 上抛，编排层停止重试，UI 引导输入新凭证（6.7）
     └─ 抛 KdbxError(MergeError 预检不可行，此步仅加载) ──► 常规错误上抛
  2. localKdbx = arrayBufferToKdbx(request.data, …)      // 双模式兼容
  3. localKdbx.merge(remoteKdbx)
     └─ 抛 KdbxError(MergeError)：根组 UUID 不同（不是同一数据库）──►
        常规错误上抛（提示"远端文件已被替换为不同数据库"）
  4. merged = localKdbx.save()
  5. write(path, merged, { expectedVersion: remoteVersion })   // 用刚读到的版本做条件写
   6. 成功 ──► isMerge = true；merged 落盘字节回传（SuccessMessage.data），
      Worker 模式下另附合并后模型的 KPSN 快照（SuccessMessage.snapshot），
      主线程 handleSuccess 走现有 isMerge 分支重建 database + DATABASE_RELOAD
```

要点：
- 步骤 5 用 `remoteVersion` 而非原始 `expectedVersion` 做条件写：合并已纳入远端变更，只需保证"读远端→写"之间没有第三方再写入；若发生（`VERSION_CONFLICT`），回到 6.1 步骤 1 重来
- 步骤 6 的 `SuccessMessage.data` 在 Worker 模式下是 merged 加密 ArrayBuffer（另附 `snapshot` 快照），主线程 `handleSuccess` 已有 `arrayBufferToKdbx` 重建逻辑（`KdbxSaveService.handleSuccess`，现优先用 snapshot 免解密），无需改动

### 6.4 有界重试与退避

- `MAX_CONFLICT_RETRY = 3`（keeweb 同款）
- 每轮重试前 `expectedVersion ← remoteVersion`、`baseContentHash ← remoteContentHash`（用最新事实做新基线）
- 重试间无需 sleep（每轮都有网络 IO，天然有间隔）；若 3 轮后仍冲突，判定"对端正在持续写入"，失败返回，本地修改保留在内存 `DbFileParam.database` 中不丢失，提示用户稍后手动重试
- 不做指数退避（保存是用户前台操作，3 次网络往返已足够感知异常）

### 6.6 错误映射与用户提示

| 内部错误 | 判定 | 用户提示 | 编排层行为 |
|---------|------|---------|-----------|
| `StorageError(VERSION_CONFLICT)` 且 retry<3 | code 判定 | （静默重试，复用"正在合并"文案） | 重读+合并+条件写 |
| `VERSION_CONFLICT` 且 retry=3 | code 判定 | "远端文件持续变化，请稍后重试保存。本地修改已保留" | 失败返回，不动 DbFileParam |
| 远端 `KdbxError(InvalidKey)`（merge 时） | `error.code === InvalidKey`（kdbxweb ErrorCodes） | "远端数据库密码已被修改，请输入新密码以完成合并保存" + 弹出密码输入框 | 停止重试；新凭证走 `mergeAndSave` 的专用重放入口（ChangePassword 页面已有凭证变更链路可复用） |
| `KdbxError(MergeError)`（根组 UUID 不同） | `error.code === MergeError` | "远端文件已被替换为不同的数据库，无法自动合并。可将本地修改另存为新文件" | 失败返回；UI 提供"另存为"（现有导出能力） |
| 常规 IO/认证错误 | 现有 `KdbxUtils.kdbxErrorMessage` | 现有文案 | 现有行为 |

## 7. 数据安全层（L3）

1. **Entry History（已有，不动）**：merge 冲突以"最后修改时间胜出 + 被覆盖版本进 History"语义工作，是丢数据的最后防线
2. **editState 墓碑（本方案启用）**：见 6.5
3. **合并前安全备份（可选，独立开关）**：merge 子流程写回前，将 `remoteContent` 原样存入应用沙箱 `files/backup/<fileName>.<timestamp>.remote.bak`（保留最近 3 份，滚动清理）。默认关闭，用户在设置中开启。成本低（远端内容已在内存），提供"合并算法出 bug"时的物理兜底
4. 敏感数据处理遵循仓库既有规范：`remoteContent`/merged 内容仅在内存与 Worker 间流转，不新增明文落盘（备份文件本身是加密的 KDBX）

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| WebDAV 服务器不支持 MOVE/锁 | tmp+MOVE 失效 | 能力探测降级为"复核后直接 PUT"；双基线 + 重试仍保证正确性 |
| 弱 ETag 误判冲突 | 多余 merge（不丢数据，性能损耗） | version 复合串以 lastModified 为主；merge 结果与远端一致时写回无害 |
| contentHash 每次保存多算一次 SHA256 | 毫秒级 CPU | KDBX 通常 <5MB；Worker 模式下不在主线程 |
| 对端同步工具（rclone 等）改 mtime 不改内容 | 误判"已变"触发 merge | merge 幂等（kdbxweb 按 UUID+时间戳），无实质影响 |
| preferences 中 editState 体积 | 每 entry 一条时间戳记录 | KDBX 规模（数千条目）下 <100KB，可接受；异常时直接丢弃（仅降精度不丢数据） |
| 双模式行为漂移 | 同步/Worker 不一致 | 新逻辑全部收敛在共享类 DatabaseSave/DatabaseLoad；9.1 的序列化往返测试守住边界 |
