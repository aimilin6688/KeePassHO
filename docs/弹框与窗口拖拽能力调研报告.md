# 弹框拖拽定位 & 应用窗口纵向拖拽 —— 鸿蒙官方文档调研报告

> 调研日期：2026-07-16
> 范围：仅检索官方文档与本项目现有实现，**未修改任何代码**。
> 目标：① 弹框（底部面板）能否拖拽调整位置；② 应用整个窗口能否纵向上下拖拽移动（而非只能缩放）。

---

## 一、结论速览

| 诉求 | 官方是否原生支持 | 结论 |
|------|----------------|------|
| 弹框自由拖拽到屏幕任意位置 | ❌ 不支持 | `bindSheet` 是**锚定式**面板（默认底部，可设居中），拖拽只能「在高度档位间切换 / 下拉关闭」，不能把弹框拖到任意坐标。需自行实现（PanGesture 或改为子窗口）。 |
| 应用窗口纵向拖拽移动 | ✅ 支持（有条件） | 前提是窗口处于**自由悬浮窗口模式（WINDOW_MODE_FLOATING）**。该模式下系统提供顶部横条，拖横条即可上下/左右移动，拖边缘缩放。若当前只能缩放不能纵向移动，说明窗口未处于该模式，或顶部横条不可用（被隐藏/被自定义标题栏取代）。 |

## 二、弹框拖拽调整位置（bindSheet）

### 官方文档依据

1. **《绑定半模态页面(bindSheet)》指南**
   `https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-sheet-page`
   - 原文要点：「半模态页面(bindSheet)默认是模态形式的**非全屏弹窗式交互页面**，允许部分底层父视图可见……半模态在不同宽度的设备上存在不同的形态能力，开发者对不同宽度的设备上有不同的形态诉求请参考 **(preferType)** 属性。」
   - 解读：`preferType` 决定面板形态（底部 / 居中），是**锚定**而非自由坐标定位。

2. **《半模态转场》SheetOptions API 参考**
   `https://developer.huawei.com/consumer/cn/doc/harmonyos-references/ts-universal-attributes-sheet-transition-0000001774281868`
   - `detents`：`SheetSize.FIT_CONTENT / MEDIUM / LARGE / 数值` 组成的**高度档位数组**。用户拖拽时面板在档位之间**切换高度**，不是自由移动。
   - `dragBar`：顶部拖拽把手。在 `bindSheet` 中，拖拽手势用于**下拉关闭**面板（或在 detents 间切换高度），**不提供任意位置移动**能力。
   - `mode`：`SheetMode.OVERLAY`（居中覆盖）/ `EMBEDDED`（嵌入）。
   - `showClose`：系统关闭按钮（与自定义标题栏互斥）。

3. **结论**：官方 `bindSheet` **没有**「拖拽到屏幕任意位置（自由 x/y）」的能力。它的拖拽语义是「高度档位切换 + 下拉关闭」。

### 若确实需要「可自由拖拽的弹框」，官方/社区可行方案

- **方案 A — 自定义浮层 + PanGesture**：用 `Stack` 覆盖层承载弹框内容，绑定 `PanGesture`，在 `onActionUpdate` 中累加偏移量更新 `@State` 位置，实现任意拖动。思路与下方「全局悬浮窗」的拖拽一致。
- **方案 B — 改为应用子窗口**：`windowStage.createSubWindow(...)` 创建子窗口，置于自由悬浮模式，用 `PanGesture` + `moveWindowTo(x,y)` 实现像悬浮窗一样自由拖动（见第三节官方示例）。**本项目 `LockScreenService.ets:69` 已用 `lockWindow.moveWindowTo(0,0)` 移动锁屏子窗口，可直接借鉴此模式。**

## 三、应用窗口纵向拖拽移动

### 官方文档依据

1. **《窗口模式简介》（核心）**
   `https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/window-mode-overview`
   - 「**主窗在自由悬浮窗口模式下固定存在顶部横条，用户可通过拖拽顶部横条移动该窗口、切换窗口模式等。用户可通过拖拽窗口边缘对窗口进行缩放。**」
   - 「对于应用子窗口、全局悬浮窗、模态窗口及系统窗口：固定以自由悬浮窗口模式显示……**支持通过 resize()、moveWindowTo() 等接口自由改变窗口大小和位置**。」
   - 反面对比：非自由悬浮模式（全屏 / 分屏）下「不支持通过 resize()、moveWindowTo() 等接口自由改变窗口大小和位置」。

2. **《多设备窗口模式最佳实践》**
   `https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-multi-device-window-mode`
   - 「自由悬浮多窗：自由窗口的大小和位置可自由调整。」「**电脑** 支持……**自由多窗(默认)**」。
   - `WINDOW_MODE_FLOATING` 代表自由多窗 / 自由悬浮窗模式。

3. **《如何实现全局悬浮窗功能》（moveWindowTo + PanGesture 官方示例）**
   `https://developer.huawei.com/consumer/cn/doc/architecture-guides/common-v1_26-ts_c264-0000002547696686`
   - `moveWindowTo(x, y)`：「移动窗口位置，基于窗口左上角顶点改变当前窗口位置」。
   - 拖拽实现：`PanGesture` 的 `onActionUpdate` 中 `windowPosition.x += event.offsetX; windowPosition.y += event.offsetY; window.moveWindowTo(windowPosition.x, windowPosition.y);`，并用 `topRectHeight / bottomRectHeight` 做纵向边界约束。

4. **window API 参考**
   `https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-window-0000001821003269`
   - `Window.moveWindowTo(x: number, y: number): Promise<void>`
   - `Window.setWindowMode(mode: WindowMode): Promise<void>`、`WindowMode.WINDOW_MODE_FLOATING` 等枚举。

### 对你现象的诊断（结合本项目，仅读未改）

- `EntryAbility.ets` **未调用** `setWindowDecorVisible(false)`，也**未设置**窗口模式 → 主窗口保留系统默认装饰栏/顶部横条。
- 若在 **PC / 2-in-1 / 平板（开启自由多窗）** 上运行，默认即自由悬浮模式，理论上**拖顶部横条即可上下左右移动**，拖边缘缩放。
- 「能缩放、不能纵向移动」的可能原因：
  1. 运行设备/形态**未处于自由悬浮模式**（如手机全屏、或分屏态）——此时系统本就不提供移动；
  2. **顶部横条被自定义标题栏遮挡或装饰被隐藏**（尽管本仓库 EntryAbility 未隐藏，需确认是否由其它 Ability/子窗口或主题生效）；
  3. 用户在拖**窗口体**而非顶部横条（系统只认顶部横条作为移动把手）。

### 可选实现方向（待你确认后再改）

- **方案 1（零代码，确认模式即可）**：确保运行设备支持自由多窗且窗口处于自由悬浮模式，直接拖系统顶部横条移动。
- **方案 2（自定义拖动区）**：若要在窗口体内任意位置拖动，或装饰栏被隐藏，可仿 `LockScreenService` 的做法——在自定义标题栏/拖动区绑定 `PanGesture`，`onActionUpdate` 中调用主窗口 `moveWindowTo(x,y)`（主窗口需先 `getMainWindow()` 取得 `Window` 实例）。
- **方案 3（强制窗口模式）**：在 `startAbility` 的 `StartOptions` 中指定 `windowMode` 为 `WINDOW_MODE_FLOATING`，或在取得主窗口后 `setWindowMode(WindowMode.WINDOW_MODE_FLOATING)`。

## 六、补充调研：拖「底部边框」只调整窗口高度（单向缩放）

> 你的澄清诉求：拖拽应用**底部边框**时，**只改变窗口高度**，而不是同时等比改变高度和宽度。

### 6.1 官方结论

1. **单向缩放本就是自由窗口的默认能力，无需特殊 API。**
   官方《应用窗口缩放适配》明确：「主窗口和带标题栏的子窗口**默认可以通过热区拖拽进行窗口大小缩放**」。在真正的**自由窗口（自由悬浮模式）**下，系统热区遵循标准规则——**拖窗口某条边（上/下/左/右）= 只改该单一维度；拖窗口四个角 = 同时改宽高**。
   → 也就是说，「拖底边只改高度」**是自由窗口的原生默认行为**，正常情况下不需要写任何代码。

2. **出现「拖底边却等比同时改宽高」，几乎可以锁定为下面两种成因之一：**

   - **成因 A（最可能）——应用未声明大屏设备类型，PC 上以「兼容模式/等比缩放窗口」运行。**
     当一个只面向手机/平板、未做大屏适配的应用运行在 PC / 2in1 上时，系统不会给它真正的自由窗口，而是套一个**固定手机比例的等比缩放窗口**：这种窗口拖任何边/角都**只能整体等比放大缩小**，无法独立调宽或调高——现象与你描述完全吻合。
   - **成因 B（次要）——窗口内容宽高比被 `setAspectRatio()` 锁定。**
     官方《窗口布局》：`setAspectRatio()`「设置窗口内容布局的比例，**该比例参数默认持久化保存**」。一旦锁定，拖动任一维度会强制另一维度按比例联动，表现即「拖底边宽度也跟着变」。可用 `resetAspectRatio()` 取消。

### 6.2 控制窗口缩放行为的官方 API

| 接口 | 作用 | 对本诉求的意义 |
|------|------|--------------|
| `setWindowLimits({minWidth,minHeight,maxWidth,maxHeight})` | 限制窗口最小/最大宽高 | 约束高度可调范围，但**不改变「拖边=单维度」的规则** |
| `setResizeByDragEnabled(enable)` | 启用/禁用整个拖拽缩放 | 只能整体开关，无法只锁宽度不锁高度 |
| `setAspectRatio(ratio)` / `resetAspectRatio()` | 锁定 / 解锁内容宽高比 | **要实现「拖底边只改高度」，必须确保没有锁定宽高比**（若曾设过要 reset，注意其持久化） |
| `deviceTypes` / `supportWindowMode`（module.json5） | 声明设备类型与支持的窗口模式 | 决定应用能否在 PC 上以**真正自由窗口**运行（而非等比兼容窗口） |

### 6.3 结合本项目核对（仅读未改）

- `entry/src/main/module.json5`：
  - `deviceTypes` 仅为 `["phone","tablet"]`，**未包含 `"2in1"`** → 未声明大屏/PC 适配，**高度吻合「成因 A（PC 兼容模式等比缩放）」**。
  - **无 `supportWindowMode` 字段**（默认含 floating），也无 `ohos.ability.window.*` 尺寸/最大化配置。
- 代码检索：**全项目未调用** `setAspectRatio` / `setWindowLimits` / `setResizeByDragEnabled`（仅 `LockScreenService.ets:68` 有一处 `resize()` 用于子窗口铺满，与主窗口缩放无关）→ **排除成因 B**（当前没有主动锁比例）。
- 综合判断：**当前「拖底边等比同时改宽高」最可能是因为应用未声明 `2in1` 大屏设备类型、在 PC 上以兼容模式（固定比例等比缩放窗口）运行所致，而非代码锁定了宽高比。**

### 6.4 可选实现方向（待你确认后再改，本次不动代码）

1. **根因方案（推荐）——让应用以真正自由窗口运行：**
   - 在 `module.json5` 的 `deviceTypes` 增加 `"2in1"`，声明大屏/PC 支持；
   - 对页面做大屏**自适应/响应式布局**适配（避免拉伸挤压）；
   - 确保**不锁定宽高比**（不调用 `setAspectRatio`，或运行时 `resetAspectRatio()`）。
   - 满足后，PC 上即为自由窗口，**拖底边=只改高度、拖角=改宽高**为系统默认，无需额外写缩放逻辑。
2. **辅助约束——** 用 `setWindowLimits` 设置合理的最小/最大高度（如 `minHeight`/`maxHeight`），限制高度可调范围，同时保留单向缩放规则。
3. **注意**：在**纯手机/平板全屏形态**下，应用本就全屏显示，系统不提供「拖边缩放窗口」的能力——此诉求只在 PC / 2in1 / 平板自由多窗形态下才成立。
