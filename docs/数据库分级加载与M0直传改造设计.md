# 数据库分级加载与 M0 直传改造设计

> 状态：设计定稿 v1（待实施）
> 关联：`数据库异步加载保存与大文件OOM治理设计.md`（v8，S1-S7 主干）、`KDBX跨线程数据传输优化设计-二进制快照协议.md`（KPSN v1/v2）、`KDBX文件存储与加载流程分析.md`、`大文件OOM治理验收测试计划.md`
> 前置结论：本文档基于 2026-10-08 真机日志（82KB 坚果云 WebDAV 库，worker 模式冷启动打开全程 3.3s）的根因量化分析制定。

## 0. 背景与问题定位

### 0.1 实测日志时间线（2026-10-08，82.5KB 库，WebDAV dav.jianguoyun.com）

| 时刻 | 阶段 | 耗时 | 归属 |
|---|---|---|---|
| ~28.87 | Worker 冷启动（isolate + 全存储栈模块加载；日志中 worker 线程 `axios createInstance` 即 `FileStorageFactory` 构造时初始化 6 种存储所致） | 估 0.1-0.3s | worker 独有 |
| 28.91→30.586 | 下载 82.5KB（`load stage download: 1673 ms`） | **1673ms** | 冷 TLS 握手（DNS+TCP+TLS 占大头，纯传输很小） |
| 30.586→31.366 | argon2 + 解密 + 解压 + XML 解析（`load stage parse: 778 ms`） | 778ms | 两模式共有 |
| 31.37→31.647 | KPSN 序列化 265ms + M0 包裹 12ms（`DatabaseLoadWorker.ets:112-118`） | 277ms | **worker 独有** |
| 31.647→32.232 | 主线程 M0 解包 7ms + `Kdbx.loadSnapshot` 重建模型 578ms（`KdbxUtils.ets:370-381`、`Password.ets:598`） | 585ms | **worker 独有** |

点击解锁 → DatabaseView 可见 ≈ 3.3s；同等小库在旧主线程模式（S1 之前生产路径）约 1.2-1.5s，回归 ≈ 2-3s，与用户体感一致。

### 0.2 打开慢的三根因（量化）

| 编号 | 根因 | 量化 | 位置 |
|---|---|---|---|
| R1 | **跨线程协议税**：模型被完整构建两次（Worker 解析→`saveSnapshot` 序列化 265ms→主线程 `loadSnapshot` 再解析 578ms） | ≈0.87s | `DatabaseLoadWorker.ets:115`、`KdbxUtils.ets:348` |
| R2 | **下载冷连接**：Worker isolate 静态不共享，只能自建 rcp session 冷握手（1673ms/82KB）；主线程启动预加载 `exists()` PROPFIND 建立的暖连接在 worker 模式下完全用不上 | ≈1s+ | `FileStorageFactory.ets:66`（每 isolate 单例）、`WebDAVStorage.ets:31-34`（同配置复用） |
| R3 | **Worker 冷启动**：懒创建（首次加载才建 isolate + 加载 kdbxweb/存储模块图） | 0.1-0.3s | `KdbxLoadService.ets:61-63` |

### 0.3 6 秒闪退（AppFreeze watchdog）根因

用户报告：大库（>4MB）操作时偶发"UI 卡顿或主线程阻塞 6s 进程闪退"。阻塞源逐项核对：

| 编号 | 阻塞源 | 规模规律 | 位置 |
|---|---|---|---|
| F1 | 主线程 `Kdbx.loadSnapshot`：整缓冲 KPSN 解析（内存 ChunkReader，无分块让出），实测 585ms@634KB 快照，随库大小线性放大；50MB 级文本库可到数十秒连续阻塞 | 线性 | `kdbx-snapshot.ts:162-247` |
| F2 | DOM 路径 XML 解析：xmldom 整棵同步构建（`STREAMING_XML_PARSE` 默认 false） | 线性（8-10×F 放大） | `kdbx-format.ts` parseXml DOM 分支 |
| F3 | 保存侧 `serializeToFile`：8MB flush 间隔内为连续同步序列化段（~200-600ms/段，段间仅 fs.write 宏任务让出；超大库单段可逼近秒级） | 线性 | `xml-utils.ts:464-499` |
| F4 | 合并路径主线程 `loadSnapshot(m0_merge_)`：同 F1 | 线性 | `KdbxSaveService.ets:187,373` |

### 0.4 设计目标（用户确认）

1. **小库（≤4MB，覆盖约 80% 用户）主线程直接打开**：零协议税、零 isolate 开销、复用预加载暖连接，打开速度恢复并优于旧主线程模式。
2. **大库（>4MB）Worker 线程打开**：下载/解密/解压等重活隔离在 Worker，主线程仅保留协作式（分块让出）解析。
3. **两路径均不触发 6s 闪退**：主线程任意连续同步段上界 ≤100ms 量级（详见 §7 冻结预算）。
4. 预加载在 worker 模式下重新生效（连接预热 + isolate 预热）。

### 0.5 非目标（如实声明）

- 不改变 KDBX 磁盘格式；不改变保存链路的存储写入语义（writeFromFile/条件写不变）。
- MERGE 路径（m0_merge_）本期保持 KPSN v1/v2 快照协议，仅列入二期 M0 v3 化候选（§8.2）。
- 文本型超大库（解压后数百 MB）仍受 CP2' 物理约束（模型必须驻 RAM），本设计改善的是"冻结/闪退"而非"总时长物理极限"。
- 保存侧 v3/AES-KDBX4 回退路径的整缓冲 `save()` 不动（既有约束）。

## 1. 总体架构

### 1.1 分级调度总览

```
                         ┌────────────────────────────────────────────────┐
                         │              KdbxLoadService.loadDatabase       │
                         │      （三处调用方统一入口：Password/DatabaseView   │
                         │        刷新 / KdbxSaveService 合并重载）          │
                         └───────────────┬────────────────────────────────┘
                                         │ resolveSize（§4.2 尺寸解析链）
                 ┌───────────────────────┴───────────────────────┐
                 │ size ≤ SYNC_LOAD_MAX_BYTES(4MB，可配置)          │ size > 阈值 或 未知
                 ▼                                                 ▼
   ┌─────────────────────────────┐              ┌─────────────────────────────────┐
   │ 主线程直开（小库）             │              │ Worker 打开（大库）                │
   │ readToFile T0(暖连接)         │              │ 预热(PREWARM)后暖连接下载 T0       │
   │ Kdbx.loadFromFile            │              │ 解密T1→解压T2→inner header       │
   │  ├ STREAMING_XML_PARSE=true  │              │  └ M0 v3 直传容器（§6，不建模型）  │
   │  └ 拉取解析器(256KB 分块协作)  │              │      ↓ 仅传路径                    │
   │ 模型（Kdbx 实例直接引用传递）   │              │ 主线程：会话解包 Reader            │
   │ SuccessMessage.data = Kdbx   │              │  └ KdbxStreamingXmlLoader 协作解析 │
   └─────────────────────────────┘              └─────────────────────────────────┘
        主线程连续同步段 ≤ ~100ms                      主线程连续同步段 ≤ ~100ms
```

**与旧架构的关键差异**：
- 调度从"编译期开关"（`ASYNC_LOAD_DATABASE`）变为"运行期按文件大小路由"，`ASYNC_LOAD_DATABASE` 降级为总开关（false 时无条件主线程，行为同今日）。
- Worker 路径的跨线程载荷从"模型 KPSN 快照"变为"原始 inner XML 直传容器（M0 v3）"，模型只在主线程构建一次。
- 两条路径共用同一拉取解析器（`KdbxStreamingXmlLoader`）与同一分块协作范式，DOM 读取路径随差分测试达标后退役。

### 1.2 三个子设计的依赖关系

```
子设计 A（存储层 getInfoOrNull）──┐
                                  ├→ 子设计 B（尺寸调度：依赖 A 的大小来源）
子设计 C（Worker 预热：独立）────┤
                                  └→ 子设计 D（M0 v3 直传：独立于 A/B/C，仅作用于 worker 路径）
```

实施顺序建议：A → C → B → D（每步独立可交付、可回归，详见 §12）。

## 2. 子设计 A：存储层 `getInfoOrNull`（exists 升级为"存在性+大小"一次返回）

### 2.1 动机与结论

预加载 `loadMostRecentFile → checkFileExists → exists()` 在 WebDAV 上内部就是一次 PROPFIND（`WebDAVStorage.ets:221` 调 `getInfo` 后**丢弃 size**）。若预加载直接取回 FileInfo，则存在性与大小一次请求同时获得，调度阶段（§4）的探测请求完全归零。

**结论：不改 `exists` 签名**（`IFileStorage.ets:64` 被 7 个实现与多处 UI 调用方依赖，`Promise<boolean>` 语义变更波及面大），**新增可选方法**（对齐 `supportsVersionFastPath?()` 的可选能力成员模式，`IFileStorage.ets:90`）：

```typescript
/**
 * 获取文件信息；文件确定不存在时返回 null，无法判定（网络错误/令牌失效等）时抛异常。
 * 可选能力：未实现的存储由调用方回退 exists()（大小未知）。
 */
getInfoOrNull?(path: string): Promise<FileInfo | null>;
```

### 2.2 各存储适配矩阵

统一模式：`exists(path)` 重写为 `(await this.getInfoOrNull(path)) !== null`，`getInfoOrNull` 复用各存储 `exists` 现有的"不存在"判定逻辑：

| 存储 | getInfoOrNull 实现 | "不存在"判定（沿用现状） |
|---|---|---|
| WebDAVStorage | `getInfo` → FileInfo；catch `WebDAVError && code===404` → null；其他异常上抛 | `WebDAVStorage.ets:220-229` |
| LocalFileStorage | `doGetInfo` → FileInfo；ENOENT/权限类不可达 → null；**注意**：现 `exists` 把一切异常吞为 false（`LocalFileStorage.ets:261-264`），新实现需区分"不存在"（null）与"无法判定"（抛），预加载语义（保留记录+提示）由 `RecentFilesService` 既有 try/catch 承接 |
| S3Storage | 按 `exists:278` 现状适配（HEAD/404 语义） | 实施时核对 |
| OneDriveStorage | 按 `exists:380` 现状适配（Graph 404） | 实施时核对 |
| HuaweiDriveStorage | 按 `exists:922` 现状适配 | 实施时核对 |
| PCloudStorage | 按 `exists:161` 现状适配 | 实施时核对 |
| FTPStorage / SFTPHandler | 按 `exists:352 / :176` 现状适配（stat/ls ENOENT） | 实施时核对 |
| CacheStorage（装饰器） | 镜像 `exists` 策略（`CacheStorage.ets:189-223`）：禁缓存→透传；forceRefresh→透传远端；onlyUseCache→缓存 stat（miss→null）；正常→远端，**远端抛异常时回退缓存副本判定**（离线可用语义不变） |

约束：`getInfoOrNull` 必须与 `getInfo` 同源（同一次远端请求形态），不允许实现成 `getInfo + catch 一切 → null`（会把"网络错误"误判为"文件不存在"，破坏 `RecentFilesService.loadMostRecentFile` 的"无法判定→保留记录"分支，`RecentFilesService.ets:253-262`）。

### 2.3 预加载接线

`RecentFilesService.checkFileExists`（`RecentFilesService.ets:283-285`）改造：

```typescript
public async checkFileExists(recentFile: RecentFile): Promise<boolean> {
  return RecentFilesService.probeFileInfo(recentFile).then(info => info !== null);
}

/** 探测并缓存：存在性 + 大小（供分级调度），探测失败上抛由调用方保留记录 */
public static async probeFileInfo(recentFile: RecentFile): Promise<FileInfo | null> {
  const manager = new KdbxFileManager(recentFile.storageType, recentFile.storageConfig);
  const storage = manager.getStorageInstance(); // 新增只读访问器，或 KdbxFileManager.getInfoOrNull 转发
  if (storage.getInfoOrNull) {
    const info = await storage.getInfoOrNull(recentFile.filePath);
    if (info !== null) {
      LoadDispatchCache.put(recentFile.filePath, info.size); // §4.2
    }
    return info;
  }
  return (await manager.exists(recentFile.filePath)) ? new FileInfoImpl() /* size 未知，仅占位 */ : null;
}
```

`KdbxFileManager` 新增转发方法 `getInfoOrNull(path): Promise<FileInfo | null>`（storage 未实现可选方法时回退：`exists` 为 true 则返回 size=0 的占位 FileInfo——**size=0 视为"未知"**，不参与调度判小，见 §4.1）。

**净效果**：冷启动预加载的网络请求次数不变（1 次 PROPFIND），同时产出调度所需大小；调度阶段缓存命中时零额外请求。

### 2.4 兼容性

- `exists` 语义与签名不变，所有 UI 调用方（WebDAVPage/OneDrivePage/S3Page/FTPPage/PCloudPage/HuaweiDrivePage 连接测试与选文件流程）零改动。
- `getInfoOrNull` 为可选方法：未适配的存储走回退路径，仅损失"大小探测"能力，调度按"未知→Worker"处理（§4.1），行为不劣于现状。

## 3. 子设计 B：尺寸解析与加载调度（小库判断）

### 3.1 调度规则

```
loadDatabase(loadParam, callback):
  if (!ASYNC_LOAD_DATABASE || !SIZE_DISPATCH_LOAD)      → 主线程（现状开关语义）
  size = await resolveSize(loadParam)                    // §3.2，含兜底探测
  if (size !== UNKNOWN && size ≤ SYNC_LOAD_MAX_BYTES)    → 主线程直开（§6.7）
  else                                                    → Worker（现状 asyncLoadDatabase + §5 预热 + §6 M0 v3）
```

| 规则 | 说明 |
|---|---|
| `size ≤ 4MB` | 主线程直开。4MB 为压缩后 KDBX 大小；默认值 `Constants.SYNC_LOAD_MAX_BYTES = 4 * 1024 * 1024`，可被 `SettingsService.KEY_LOAD_MAIN_THREAD_MAX_BYTES`（默认 4MB，暂无 UI 入口，对齐 `KEY_DATABASE_MAX_SIZE` 模式）覆盖 |
| `size > 4MB` 或 **size 未知** | Worker 路径。未知时保守走 Worker（行为不劣于现状，且 UI 保护更强） |
| `size === 0`（占位/无效） | 等同未知 → Worker |
| 级联总开关 | `Constants.SIZE_DISPATCH_LOAD = true`（kill switch，false 时恢复"恒 Worker"现状） |

**为什么保留 Worker 路径（而非全部主线程协作式直开）**：协作式解析已消除冻结（§7），但大库的 argon2/解密/解压 CPU 总量仍在秒级~十秒级，置于 Worker 可让主线程在打开期间保持满帧率；同时 Worker 对"未协作化热点"提供兜底隔离。阈值语义因此是"主线程可承受的单次等待时长"而非"内存安全边界"（内存安全仍由 CP1/CP2'/CP-DISK 守卫保证，两路径均生效）。

### 3.2 尺寸解析链（`resolveSize`，新增 `services/kdbx/LoadDispatchService.ets`）

优先级从高到低，命中即返回：

| 序 | 来源 | 新鲜度 | 成本 | 说明 |
|---|---|---|---|---|
| 1 | `LoadDispatchCache.get(filePath)`（进程内存 Map） | 最近一次探测/加载 | 0 | 写入点：①预加载 probeFileInfo（§2.3）②Worker PREWARM_RESULT（§5.1）③加载成功 SuccessMessage.fileSize 回填（§3.4） |
| 2 | `RecentFile.fileSize` 持久化字段 | 上次成功打开 | 0 | `TypeDefined.ets` RecentFile 增可选 `fileSize?: number`；`Password.putFileToRecentFile` 写入。旧记录无此字段→undefined→继续。覆盖"重启后预加载失败（离线）"场景 |
| 3 | 主线程兜底探测 `KdbxFileManager.getInfoOrNull` | 实时 | LOCAL：stat≈0；远端：warm PROPFIND ~100-300ms（仅缓存全 miss 时发生） | 探测失败/超时（WebDAV 检查类请求 3s 连接+传输上限，`WebDavClient.ets:126-133`）→ 返回 UNKNOWN → Worker |
| 4 | UNKNOWN | — | — | → Worker（保守默认） |

缓存一致性：不做失效时间戳（打开频率低、文件大小变化通常渐进）；"大小过期导致误走主线程"的后果 = 主线程多冻若干秒但无内存风险（守卫仍在），发生频率与代价可接受（§11 风险表）。

### 3.3 守卫去重（`precheckSize` 透传）

现状：`DatabaseLoad.loadKdbxFileToFile`（`DatabaseLoad.ets:105`）内 `DatabaseLoadGuard.checkBeforeRead` 会再做一次 `getInfo`（Worker 内冷连接时这次 PROPFIND 很贵）。改造：

- `LoadDatabase`（`DatabaseLoadWorkerParam.ets`）增可选字段 `precheckSize?: number`；调度层在路由前把解析到的 size 写入。
- `DatabaseLoadGuard.checkBeforeRead(fileManager, filePath, precheckSize?: number)`：`precheckSize > 0` 时跳过 `getInfo`，直接以该值执行 CP1（512MB 上限）与 CP-DISK（4×F 磁盘余量）检查；`GuardCheckResult.fileInfo` 保持 null（现有调用方 `DatabaseLoad.ets:105-111` 只消费 rejectReason，无回归）。
- 探测失败的 UNKNOWN 不写 precheckSize，守卫行为不变（fail-open）。

注意：WebDAV `readToFile` 下载后仍有一次 `getInfo` 取 ETag（`WebDAVStorage.ets:173`），该次保留（版本基线必需）。

### 3.4 SuccessMessage 增 `fileSize`

`WorkerParam.ets` SuccessMessage 增 `fileSize?: number`：

- Worker 侧：`DatabaseLoad.handleLoadDatabase` 把 `fileInfo.size` 填入（两路径通用——主线程路径同样回填）。
- 主线程侧：`KdbxLoadService.handleSuccessMessage` / `Password.handleSuccessMessage` 消费时写 `LoadDispatchCache`；`Password.putFileToRecentFile` 持久化进 `RecentFile.fileSize`。

### 3.5 调用方与边界场景矩阵

加载入口（全部经 `KdbxLoadService.loadDatabase` 统一受益，无需各自改造）：

| 入口 | 场景 | 调度行为 |
|---|---|---|
| `Password.ets:538` | 主打开（最近文件/位置选择/生物认证） | 正常调度；预加载+预热使 size 缓存近乎必中 |
| `DatabaseView.ets:1535` | refreshDatabase（强制远端刷新+合并） | 正常调度；`forceRefresh` 已在 `attachCachePolicy` 于任务消息级别注入（`KdbxLoadService.ets:58`），不受影响 |
| `KdbxSaveService.ets:185` | 保存链路版本冲突后的 MERGE 重载 | 正常调度；上一次 SuccessMessage.fileSize 已在缓存，小库重载同样提速 |

| 边界场景 | 行为 |
|---|---|
| onlyUseCache（离线） | 尺寸链第 1/2/3 步中，`CacheStorage.getInfoOrNull` onlyUseCache 分支返回缓存 stat（本地，快） |
| 探测时网络抖动失败 | UNKNOWN → Worker → 加载流程自然报真实错误 |
| 文件在他机变大（快照过期） | 误走主线程：打开变慢但守卫兜底；打开成功后 fileSize 回填自愈 |
| 双击/重复触发 | 主线程路径无 busy 概念（同步串行天然互斥）；Worker 路径沿用 workerBusy 立即拒绝（`KdbxLoadService.ets:41-49`） |

## 4. 子设计 C：Worker 预热（PREWARM 协议）

### 4.1 消息协议

`WorkerParam.ets` 新增：

```typescript
export enum MessageType {
  // ...既有...
  PREWARM = 'PREWARM',                  // 主线程 → Worker：预热请求
  PREWARM_RESULT = 'PREWARM_RESULT',    // Worker → 主线程：预热结果
}

/** 预热请求：仅元数据三要素，绝不携带密码/密钥（安全面最小化） */
export class PrewarmMessage implements WorkerMessage, CachePolicyCarrier {
  type: MessageType = MessageType.PREWARM;
  filePath: string;
  storageType: StorageType;
  storageConfig: StorageConfig;
  // CachePolicyCarrier 三字段保持 undefined —— 预热不注入策略（见 §4.4 约束 2）
}

export class PrewarmResultMessage implements WorkerMessage {
  type: MessageType = MessageType.PREWARM_RESULT;
  filePath: string;
  size?: number;        // 成功时 > 0；探测失败为 undefined
  version?: string | null;
  error?: string;       // 失败原因（仅日志用途）
}
```

加载 Worker 通道为 JSON 字符串（`DatabaseWorkerFactory.ets:23-24`），PREWARM 沿用同一序列化通道。

### 4.2 Worker 壳处理（`DatabaseLoadWorker.ets`）

```typescript
if (message.type === MessageType.PREWARM) {
  const req = message as PrewarmMessage;
  new DatabaseLoadWorker().handlePrewarm(req); // fire-and-forget，不进 taskChain
}
```

`handlePrewarm`：
1. `new KdbxFileManager(req.storageType, req.storageConfig)`——在 Worker isolate 内完成 `FileStorageFactory` 单例构造（全部存储模块图初始化，消除 R3 冷启动）与 `WebDAVStorage.init`（rcp session 创建）；
2. `getInfoOrNull(req.filePath)`（无该实现则 `exists`）——发出真实网络请求完成 TLS 握手与连接池预热（消除 R2 冷连接）；
3. 成功 → `PrewarmResultMessage{filePath, size, version}`；失败 → `{filePath, error}`；均 `workerPort.postMessage` 回主线程。

**不进 taskChain 的原因**：taskChain 串行化会在预热请求悬挂时（网络差，上限 3s）阻塞后续真实加载任务；预热是只读元数据操作，与加载任务共用同一 `WebDAVStorage` 实例（Worker 内 factory 单例 + `isSameConfig` 复用连接，`WebDAVStorage.ets:31-34`），rcp session 支持并发请求，交错执行安全。

### 4.3 `KdbxLoadService` 改造：onmessage 一次性注册 + 扇出

现状问题：`asyncLoadDatabase` 每次加载重挂 `onmessage`（`KdbxLoadService.ets:81-99`）——PREWARM_RESULT 可能在两次加载之间到达而被丢弃，或覆盖在途回调。重构为：

```typescript
private static currentCallback: KdbxLoadServiceCallback | null = null; // 在途任务回调

private static ensureWorker(): worker.ThreadWorker {
  if (KdbxLoadService.databaseWorker === null) {
    KdbxLoadService.databaseWorker = DatabaseWorkerFactory.createLoadWorker();
    // 创建时一次性注册（INIT 已由工厂 postMessage，FIFO 先于一切消息）
    KdbxLoadService.databaseWorker.onmessage = (e: MessageEvents) => {
      const data = e.data as WorkerMessage;
      switch (data.type) {
        case MessageType.PREWARM_RESULT:            // §4.2：仅更新调度缓存
          LoadDispatchCache.putFromPrewarm(data as PrewarmResultMessage);
          return;
        case MessageType.MESSAGE:  ... // 路由到 currentCallback?.onLoadMessage（原 handleLoadMessage）
        case MessageType.SUCCESS:  ... // 释放 busy + currentCallback?.onSuccessMessage + 置空 currentCallback
        case MessageType.ERROR:    ... // 同上错误分支
      }
    };
    // onAllErrors / onexit 注册逻辑原样迁移（路由 currentCallback，终态置空并释放 busy）
  }
  return KdbxLoadService.databaseWorker;
}
```

对外新增：

```typescript
/**
 * 预热常驻加载 Worker（isolate 模块图 + rcp 连接 + 大小探测）。
 * busy（加载在途）时跳过；不设置 busy；不消费 forceRefresh。
 */
public static prewarm(filePath: string, storageType: StorageType, storageConfig: StorageConfig): void {
  if (!Constants.POOL_DATABASE_WORKER || KdbxLoadService.workerBusy) return;
  try {
    KdbxLoadService.ensureWorker().postMessage(JSON.stringify(new PrewarmMessage(filePath, storageType, storageConfig)));
  } catch (e) { /* 预热失败无害：仅日志 */ }
}
```

### 4.4 约束与安全边界

| 编号 | 约束 | 理由 |
|---|---|---|
| 1 | `prewarm` 在 `workerBusy === true` 时直接跳过 | 不与在途加载任务抢通道；预热仅发生在页面展示期（用户输密码阶段），与加载任务时间窗天然错开 |
| 2 | **PREWARM 消息不调用 `DatabaseWorkerFactory.attachCachePolicy`** | 该方法会就地消费 `forceRefresh` 一次性标志（`DatabaseWorkerFactory.ets:60-62`）；若预热消费掉，`DatabaseView.refreshDatabase`（`DatabaseView.ets:1532` 设置 forceRefresh 后加载）的强制刷新语义被破坏。预热使用 Worker 当前 INIT/上次任务残留策略即可——元数据新鲜度不影响正确性 |
| 3 | PREWARM 不携带密码/密钥文件 | 攻击面最小化；与加载任务消息（含密码）严格分离 |
| 4 | 预热与后续加载必须同 storageConfig | `WebDAVStorage.init` 配置变更会 `closeClient` 杀掉在途连接（`WebDAVStorage.ets:37`）；同一最近文件场景配置恒同。配置不同（用户重登）时预热请求被取消，fire-and-forget 吞掉异常，无害 |
| 5 | 预热不创建保存 Worker | 保存低频且非本次目标；`KdbxSaveService.prewarm()` 列为可选后续项 |

### 4.5 触发点（`LoadDispatchService.prepare`，新增统一入口）

```typescript

```

| 触发点 | 覆盖场景 |
|---|---|
| `EntryAbility.preloadEssentialServices`：`loadMostRecentFile` 成功返回后（紧随 §2.3 probeFileInfo，size 已进缓存） | 冷启动最近文件流程（含生物认证秒解锁用户——预热在用户输指纹/密码期间完成） |

LOCAL 存储不预热（stat 即得 size；>4MB 的本地大库在调度选择 Worker 后懒创建 isolate，冷启动代价由该低频场景自行承担）。

## 5. 子设计 D：M0 v3 直传容器（消除双重构建，大库 Worker 路径）

### 5.1 现状问题（R1 + F1）

```
Worker： XML 解析→模型① → saveSnapshot 序列化(265ms) → M0(v1/v2 快照)
主线程： M0 解包 → loadSnapshot 再解析(578ms) → 模型②      ← 整块无让出，随库线性放大 → F1 闪退源
```

模型构建两次 + 序列化一次；且 `KdbxSnapshot.load` 用 `MemoryChunkReader` 整缓冲喂给解析器（`kdbx-snapshot.ts:235`），主线程无协作让出。

### 5.2 目标链路

```
Worker： T0 → 解密 T1 → 解压 T2 → inner header 解析（附件落盘 AS）→ 【不解析 XML】
        → M0 v3 容器流式产出（头部 blob + innerInfo + 附件池引用表 + 原始 XML 区段文件级拷贝）
主线程： 会话文件流式解包 Reader → v3 容器解析（头部/池引用）→ KdbxStreamingXmlLoader
        分块协作解析（256KB/块，块间让出）→ 模型（仅此一次构建）
```

消除项：Worker 侧 XML→模型①（~200-300ms@82KB，大库线性）、`saveSnapshot` 序列化（265ms）、主线程整块 `loadSnapshot`（578ms→换成等量协作解析）。

### 5.3 M0 v3 容器字节布局（KPSN 家族 version=3）

设计原则：**复用 KPSN v1/v2 的魔数与池条目编码**（差分测试与 `isSnapshot` 分发可沿用），新增 innerInfo 字段与"池前于 XML"的顺序（顺序消费友好：池须在解析前 importPool，`kdbx-snapshot.ts:233`）：

```
偏移    长度   字段
[0..4)   4    magic 'KPSN'
[4..6)   2    version = 3 (uint16 LE)
[6..10)  4    flags (uint32 LE)
              bit0 RAW_XML：1=xml blob 为原始 inner XML（Protected 值为内层流密文，需 innerInfo 解密）
                              0=明文快照 XML（KPSN v1/v2 语义，供 MERGE 二期复用 §8.2）
[10..14) 4    headerLen (uint32 LE)
[14..18) 4    innerInfoLen (uint32 LE)      RAW_XML=1 时 >0；=0 时为 0
[18..22) 4    poolCount (uint32 LE)
[22..26) 4    xmlLen (uint32 LE)
之后顺序：
  header blob    KdbxHeader.write 输出（外层头：version/kdf/cipher/salts，同 v1/v2）
  innerInfo blob [uint8 crsAlgorithm][uint32 keyLen][key bytes]
                 （v4 内层头字段 InnerRandomStreamID + protectedStreamKey；v1/v2 缺失导致
                   load 后按默认补 ChaCha20 的保真缺口在此修复——v3 携带真实值）
  pool entries × poolCount
                 [uint32 dataLen][uint8 flags][32B sha256][data?]（与 v1/v2 完全同构）
                 v4：inner header Binary 字段产出——大附件已落盘 AS → FLAG_STORE_REF（仅 hash+len）；
                     小附件（< attachmentsDiskThreshold，内存模式）→ inline data
                 v3(KDBX3)：poolCount=0（附件在 XML 内 base64，由拉取解析器增量解码落 AS）
  xml blob       RAW_XML=1：T2 的 XML 区段原样字节（不解码不重排）
                 RAW_XML=0：明文快照 XML（KPSN buildXml 语义）
```

池条目 flags 语义不变（`FLAG_PROTECTED=1`、`FLAG_STORE_REF=2`，`kdbx-snapshot.ts:34-36`）。

### 5.4 会话文件流式包裹格式（SessionFileService v2）

现状 `wrapToFile/unwrapFromFile` 为整缓冲 AES-256-GCM（`SessionFileService.ets:110-144`），大库 XML 会破坏"内存窗口与文件大小解耦"目标。新增**分块包裹流**（保持 [12B nonce][ct][16B tag] 的逐块 GCM 语义与既有安全模型：进程级会话密钥仅内存、authTag 完整性校验）：

```
会话包裹文件布局：
[0..4)   4   magic 'SFW1'
[4..8)   4   chunkSize (uint32 LE，固定 4MB，末块可短)
[8..12)  4   chunkCount (uint32 LE)
之后 chunkCount 个块：[12B nonce][GCM 密文 chunkSize'][16B authTag]
```

`SessionFileService` 新增 API（既有整缓冲接口保留，MERGE 路径继续使用）：

```typescript
/** 打开流式包裹写入器（Worker 产 M0 v3 用） */
public static openWrapStream(prefix: string): SessionWrapWriter;

export class SessionWrapWriter {
  /** 追加明文块：内部逐块 GCM seal（nonce 每块随机）+ fs.write，内存窗口 = 单块 */

  /** 收尾（写 manifest 头 + fsync + close），返回会话文件路径；不调用则文件残缺由清扫兜底 */

/** 打开流式解包顺序读取器（主线程消费 M0 v3 用） */

```

### 5.5 Worker 产出端：`Kdbx.loadToContainerFile`

kdbxweb 新增（`kdbx.ts` 薄包装 + `kdbx-format.ts` 实现）：

```typescript
/**
 * 流式加载到 v3 直传容器：T0→解密 T1→解压 T2→inner header 逐字段（附件落盘 AS）
 * → 容器头部（fixed + header blob + innerInfo + pool）内存构建（KB 级）
 * → XML 区段从 T2 文件分块（4MB）拷入 containerWriter —— 全程不构建模型、
 * 不 materialize 整段 XML（内存窗口 ≈ 单块 + 附件落盘窗口）。
 * 仅 v4+ChaCha20+GZip 走此快路径；v3/AES-KDBX4 整缓冲解密后落 T2 再走同一容器产出
 * （与 S5 parseInnerFileStreaming 的格式分流一致）。
 */
static loadToContainerFile(
  t0Path: string,
  credentials: KdbxCredentials,
  options: {
    t1Path: string;
    t2Path: string;
    attachmentStore?: AttachmentStore;
    attachmentsDiskThreshold?: number;
    containerWriter: ContainerChunkWriter;   // { writeChunk(Uint8Array): Promise<void> }
  }
): Promise<void>;
```

实现要点：
1. 复用 `prepareInnerFileStreaming`（ISIZE 预检 + inflateFile）与 `readInnerHeaderFromFile`（`kdbx-header.ts`，Binary 字段 ≥阈值 `sha256FileRegion + putFromFileRegion` 落盘产出 `KdbxBinaryDiskRef` 池条目——v3 容器池条目直接取自此产物，含 hash/len/protected 标志）。
2. `readInnerHeaderFromFile` 需额外返回 `xmlStartOffset` 与 `protectedStreamKey/crsAlgorithm`（现返回值已有前两者上下文，实施时核对签名）。
3. 容器头部字节在内存拼装（header blob + innerInfo + 池元数据均为 KB 级），经 `writeChunk` 一次写出；随后以 4MB 循环 `fs.read(T2, offset=xmlStart)` → `writeChunk` 直至 XML 区段末尾。
4. CP2' 前置检查：`xmlLen = stat(T2).size − xmlStart`，超 `maxDecompressedBytes` 直接抛 `DecompressedTooLarge`（与 `KdbxSnapshot.load:184-189` 同语义）。
5. 失败即抛（v1/v2 快照路径的"守卫错误不回退"原则不变，`DatabaseLoad.ets` finally 清理 T0/T1/T2 既有逻辑复用）。

`DatabaseLoadWorker.postSuccessMessage`（`DatabaseLoadWorker.ets:112-124`）改造：

```typescript
// 旧：const snapshotBytes = await KdbxUtils.kdbxToArrayBuffer(kdbx); wrapToFile(...)
// 新：fast path（loadToContainerFile 成功）→ m0Path + data 空缓冲，直接 post
//     降级路径（容器产出抛 UnsupportedFormat 等）→ 既有 Kdbx.loadFromFile + saveSnapshot + wrapToFile（v1/v2）
```

降级触发条件：非 v4/非 ChaCha20 且整缓冲分支失败、`containerWriter` 注入失败、`AttachmentStore` 不可用（v4 磁盘引用附件恢复必需，`kdbx-snapshot.ts:216-221` 同款校验前置）。降级仅影响性能不影响正确性。

### 5.6 主线程消费端：`KdbxSnapshot.loadFromReader`

kdbxweb 新增（`kdbx-snapshot.ts`）：

```typescript
/**
 * 从顺序字节流加载 v3 容器（会话解包 Reader 或测试用内存 Reader）。
 * 协作式：XML 区段经 ChunkReader 适配器按 256KB 喂给 KdbxStreamingXmlLoader，

  credentials: KdbxCredentials,
  options?: { maxDecompressedBytes?: number; attachmentStore?: AttachmentStore }
```

流程：
1. 顺序读 fixed header（26B）→ 校验 magic/version=3 → 读 flags/headerLen/innerInfoLen/poolCount/xmlLen；

3. 读 header blob → `KdbxHeader.read`；读 innerInfo → `header.protectedStreamKey/crsAlgorithm` 赋值（RAW_XML=1 必须存在，缺失抛 InvalidState——比 v1/v2 默认补 ChaCha20 的保真更强）；

5. 剩余流包装为 `StreamReaderChunkReader implements ChunkReader`（256KB 读取 + 复用 `decodeUtf8Chunk` 的 UTF-8 跨块边界处理，`xml-pull-parser.ts:154-178`）→ `KdbxStreamingXmlLoader.load`（`tryCreateSaltGenerator` 检测到 protectedStreamKey+crsAlgorithm → 内流解密模式，`xml-pull-parser.ts:1304-1312`）；
6. v3(KDBX3) XML 内 base64 附件由解析器增量解码落 AS（S6 既有能力）。

## 6. 冻结预算分析（6s watchdog 论证）

**判定原则**：主线程连续同步段上界 ≤100ms 量级；所有让出必须是**真实宏任务边界**（fs.read/fs.write/rcp 回调/setTimeout(0)），Promise 微任务链不算让出。

### 6.1 小库主线程路径

| 阶段 | 执行位置 | 连续主线程占用上界 | 让出机制 |
|---|---|---|---|
| 下载 readToFile（远端） | rcp native | ≈0 | 系统回调 |
| 守卫/探测 getInfoOrNull | 网络 | ≈0 | 网络异步（连接类 3s 上限） |
| argon2 KDF | 原生 napi | **待确认项 #1**：若异步 ≈0；若同步实现则一次性 ~0.5-0.8s（<6s，不致死但刺眼） | `@ohos-rs/argon2` 实施时核对；若为同步且阈值内不可接受，将 KDF 调用包一层 taskpool 或维持 Worker 路径 |
| HMAC 块验证+ChaCha20 解密 T0→T1 | 主线程 | ~20-40ms / 1MB 块 | 块间 fs 读写宏任务（`hmac-block-transform.ts` 文件版） |
| inflate T1→T2 | 原生 zlib napi | ≈0 | napi 异步（libuv 线程池） |
| inner header + 附件落盘 | 主线程 | ~10-30ms / 4MB 块 | 块间 fs IO |
| XML 拉取解析 | 主线程 | ~2-10ms / 256KB 块 | 块间 fs.read 宏任务 |
| computeHashes/pending 解析 | 主线程 | <50ms（一次性，模型量级） | — |

最坏连续段 ≈ 50ms（除确认项 #1）→ **远低于 watchdog**。总时长（≤4MB，典型 <1MB 库）：~1-2.5s。

### 6.2 大库 Worker 路径（M0 v3）

| 阶段 | 执行位置 | 主线程占用 | 说明 |
|---|---|---|---|
| 下载/argon2/解密/解压/容器产出 | Worker | 0 | 重 CPU 全隔离 |
| M0 会话解包 read | 主线程 | ~10-30ms / 4MB GCM 块（cryptoFramework 原生） | 块间 fs.read 宏任务 |
| XML 拉取解析 | 主线程 | ~2-10ms / 256KB | 同 6.1 |
| F1（loadSnapshot 整块） | — | **已消除** | v3 不再走 `KdbxSnapshot.load` |

### 6.3 保存路径（配套治理，F3）

`serializeToFile`（`xml-utils.ts:464`）现状 8MB flush 间隔为连续同步段（~200-600ms），段间仅 fs.write 宏任务。改造：`flush()` 内 `fs.write` 后追加 `await new Promise<void>(r => setTimeout(r, 0))` 强制渲染让出（仅在主线程调用时启用，Worker 侧传入 `yieldBetweenFlushes=false` 以免白付延迟）。合并路径 F4 列二期（§8.2）。

### 6.4 结论

| 目标 | 论证 |
|---|---|
| 小库不闪退 | 主线程任意连续段 ≤~50ms（6.1），无整块解析/整块快照 |
| 大库不闪退 | F1/F2 消除（v3 协作解析 + 拉取解析器默认化）；F3 由 flush 让出治理；主线程仅剩分块解包+分块解析 |
| 大库总时长 | 单次解析（对比现状双解析+序列化），不劣于现状且显著优于现状 |

## 8. 保存 / MERGE 路径影响与二期项

### 8.1 保存（本期最小治理）

- 主线程 `serializeToFile` flush 让出（§6.3）——唯一必改；保存 Worker 链路、writeFromFile、条件写、版本基线全部不动。
- 保存入口不参与尺寸调度（`ASYNC_SAVE_DATABASE` 恒 true）：保存无用户在途等待预期，Worker 化收益稳定。

### 8.2 MERGE 二期候选（本文档不实施）

`KdbxSaveService` 合并重载与 `m0_merge_` 仍走 KPSN v1/v2 整缓冲（F4 残留）。二期方案：合并产物改写 **v3 容器 flags=0（明文快照 XML）**——Worker 内 `serializeToFile`（明文保护值形态）产出 XML 文件 + 池引用 → 同一分块包裹；主线程 `loadFromReader` 复用。容器/读取器代码完全复用，仅产出端一个变体，预计 0.5-1 天。触发条件：出现大库 MERGE 闪退报告或验收测试复现。

## 9. 配置开关与回滚

| 开关 | 默认 | 关闭效果 | 层级 |
|---|---|---|---|
| `Constants.ASYNC_LOAD_DATABASE` | true | false：无条件主线程（现状语义，叠加 streamingXmlParse 默认值变化） | 总 |
| `Constants.SIZE_DISPATCH_LOAD` | true | false：恒 Worker（= 当前生产行为） | 调度 |
| `SettingsService.KEY_LOAD_MAIN_THREAD_MAX_BYTES` | 4MB | 调 0 → 恒 Worker；调大 → 更多库走主线程 | 阈值 |
| `KdbxFormat.streamingXmlParse` | **true（本设计起）** | false：DOM 路径（差分对照/回滚） | 解析器 |
| M0 v3 降级路径 | 自动 | `loadToContainerFile` 抛 UnsupportedFormat → Worker 内回退 KPSN v1/v2 全模型路径（行为=现状） | 容器 |
| PREWARM | 无独立开关 | 出错即静默跳过，等效未预热 | 预热 |

回滚组合保证：任一子设计故障均可独立退回现状行为，无数据格式迁移（KDBX 磁盘格式与会话文件均为进程内临时态）。
