## 1. 背景与现状

### 1.1 问题现象

通过 Password 页解锁打开数据库，每次都全量下载远端文件，即使远端未发生任何变化、本地缓存中已有一份逐字节相同的副本。大库（10MB+）在慢速 WebDAV 下打开耗时以十秒计（S8 实测华为云盘 11.8MB 下载 6.7s，~1.8MB/s）。

### 1.2 现状链路（代码核实）

```
Password.ets 解锁
 └─ KdbxLoadService.loadDatabase
     └─ 分级调度 resolveSize（LoadDispatchCache / RecentFile.fileSize / 兜底 getInfoOrNull）
     └─ DatabaseLoad.handleLoadDatabase（DatabaseLoad.ets:29-158）
         └─ loadKdbxFileToFile（DatabaseLoad.ets:176-194）
             ├─ DatabaseLoadGuard.checkBeforeRead（getInfo；precheckSize 已知时跳过，DatabaseLoadGuard.ets:52）
             └─ fileManager.readToFile(filePath, t0Path)     ← 无条件全量 GET 下载
                 └─ CacheStorage.readToFile（CacheStorage.ets:148-149）
                     └─ 正常模式：直接委托 decoratedStorage.readToFile，不读缓存、下载后也不回填缓存
         └─ Kdbx.loadFromFile(t0) 流式解密 → sha256HexFile(t0) 冲突基线 → 删除 T0
```

### 1.3 根因清单

| # | 根因 | 位置 |
|---|------|------|
| R1 | 加载编排层无条件 `readToFile` 全量下载，守卫 getInfo 拿到的 `version` 被丢弃（保存侧早已用它做快速路径） | `DatabaseLoad.ets:186-191` |
| R2 | **流式加载根本不更新本地缓存**：`CacheStorage.readToFile` 正常模式只委托远端，下载内容既不落缓存、更无版本元数据 | `CacheStorage.ets:148-149` |
| R3 | 缓存是裸文件 `<hash>.cache`，`getCacheInfo` 用 fs.stat 伪造 FileInfo，**无 version 字段**，"缓存内容对应远端哪个版本"这一事实无处记录 | `CacheStorage.ets:439-461`、`CacheConstants.ets:62-76` |
| R4 | WebDAV 未声明版本可信（`supportsVersionFastPath` 缺失），即使有版本事实也不参与任何快速决策 | `WebDAVStorage.ets`（无该方法） |

> R2 是 R3 的前置洞：不先补"下载后回填缓存 + 记录版本"，任何版本比对都无米下炊。这也是本计划 P2 先于 P3 的原因。

## 2. 目标与非目标

### 目标

- G1 远端版本未变时，打开数据库从「全量 GET」降为「1 次元数据请求（PROPFIND/HEAD）+ 1 次本地文件拷贝」，跳过下载
- G2 命中快速路径后，冲突检测基线三元组（`modifiedTime / version / contentHash`）语义不变：仍以远端事实与 T0 实算哈希为准
- G3 同步模式与 Worker 模式行为完全一致（逻辑全部落在共享层 `DatabaseLoad`，无消息协议改动）
- G4 fail-safe：任何缓存/meta 缺失、损坏、不匹配都安全退化为现状全量下载，绝不因快速路径引入错数据
- G5 现有语义完整保留：`force_refresh`（下拉刷新/冲突重载）、`only_use_cache`（离线）、关闭本地缓存开关

### 非目标

- N1 不做缓存内容哈希校验（D2：格式层 HMAC 已兜底）
- N2 不改 Worker 消息协议（`LoadDatabase` 参数零新增）
- N3 不做后台自动同步/预下载（保存仍用户触发）
- N4 不动 `read()` 整缓冲路径的缓存行为（密钥文件等小文件场景，见 §5 P2 边界）

## 3. 方案总览

```
DatabaseLoad.loadKdbxFileToFile（改造后）
 ├─ fast候选 = fileManager.supportsVersionFastPath() && CacheMetaService.readMeta(path) !== null
 ├─ 守卫 checkBeforeRead：
 │    fast候选 → 不传 precheckSize，强制 getInfo 拿远端 version（1 次元数据请求）
 │    非候选   → 现状优化（precheckSize 已知则跳过 getInfo）
 ├─ fast候选 && guardInfo.version === meta.version && guardInfo.size === meta.size
 │    → CacheStorage.readCacheToFile：fs.copyFile(缓存, T0)，跳过下载
 │    → fileInfo = guardInfo（远端事实作为基线）
 ├─ 否则 → fileManager.readToFile（现状全量下载，P2 起顺带回填缓存+meta）
 └─ 后续不变：Kdbx.loadFromFile(T0) → sha256HexFile(T0) → SuccessMessage(基线三元组) → 删 T0
```

**核心思想**：与保存侧 `DatabaseSave.ets:96-111` 完全对称——接口层提供"能力"（`supportsVersionFastPath`）与"事实"（`FileInfo.version`），缓存层提供"本地版本记录"（meta sidecar），编排层做"决策"（命中拷贝 / miss 下载）。各存储互不感知，零 provider 分支。

### 快速路径命中前提（全部满足才命中，任一不满足即 miss）

1. 存储声明版本可信：`supportsVersionFastPath() === true`
2. 缓存元数据存在且有效：`meta.version !== null`
3. 守卫成功取得远端事实：`guardInfo !== null && guardInfo.version !== null`
4. **版本相等**：`meta.version === guardInfo.version`
5. **尺寸相等**：`meta.size === guardInfo.size`（对弱 ETag / 秒级 mtime 的第二道防线）
6. 缓存文件存在且本地拷贝成功
7. 非 `force_refresh` / 非 `only_use_cache` / 本地缓存开关开启

### P2 CacheStorage.readToFile 正常模式回填缓存 + meta（补 R2/R3 洞）

| 项 | 内容 |
|---|---|
| 文件 | `entry/src/main/ets/storage/cache/CacheStorage.ets`（`readToFile`，现 :128-150） |
| 改动 | 正常模式分支：远端下载完成后 **await** `fs.copyFile(destPath, cachePath)` + `CacheMetaService.writeMeta(path, { version: info.version ?? null, size: info.size, modifiedTime: info.modifiedTime, savedAt: Date.now() })`，再返回 `info`。回填失败仅记日志（透明，缓存始终 best-effort） |
| 为什么必须 await | `destPath` 是调用方临时文件（T0），`DatabaseLoad` 的 finally 会删除；异步拷贝会与删除竞态 |
| 版本来源零成本 | 装饰层 `readToFile` 的返回 `FileInfo` 本就带 version：WebDAV 真流式实现下载后 `getInfo`（`WebDAVStorage.ets:182`）；未迁移存储走 `FileTransfer.readToFileDefault` 末尾同样 `getInfo`（`FileTransfer.ets:33`）。**无需任何新增请求** |
| 边界（不改） | ① 仅缓存模式 / 强制刷新分支维持现状；② `read()` 整缓冲路径不写 meta（该路径现仅服务密钥文件等小文件，数据库主链路已全流式化）；无 meta → 下次快速路径 miss → 重新下载回填，安全方向 |
| 成本 | 一次本地文件拷贝（flash 顺序写，20MB 库 <1s），相对省下的全量网络下载净赚 |

### P3 加载版本快速路径（核心，D1：放 DatabaseLoad 编排层）

#### P3.1 接口契约（IFileStorage 可选能力）

```ts
/**
 * 版本快速路径：expectedVersion/expectedSize 与本地缓存元数据一致时，
 * 将缓存内容复制到 destPath，返回 true（命中）；否则返回 false（miss），
 * 调用方回落 readToFile 全量下载。仅 CacheStorage 装饰器实现。

  expectedSize: number): Promise<boolean>;
```

| 实现方 | 行为 |
|---|---|
| `BaseFileStorage` | 默认 `return false`（LOCAL 存储不经 CacheStorage 包装，本地文件天然无需缓存快速路径） |
| `CacheStorage` | 见下 |
| `KdbxFileManager` | 透传：`return this.storage.readCacheToFile?.(...) ?? false` |

#### P3.2 CacheStorage.readCacheToFile 实现

```ts
public async readCacheToFile(path: string, destPath: string,
  expectedVersion: string, expectedSize: number): Promise<boolean> {
  if (!CacheConstants.isEnableLocalCache()) { return false; }         // 关缓存：透传远端
  if (CacheConstants.getOnlyCache()) { return false; }                // 仅缓存：由 readToFile 仅缓存分支负责
  if (CacheConstants.getForceRefresh()) {
    CacheConstants.clearForceRefresh();                               // 消费标志：快速路径跳过了 readToFile，
    return false;                                                     // 不清会把 force 泄漏给下一次保存
  }
  const meta: CacheMeta | null = CacheMetaService.readMeta(path);
  if (meta === null || meta.version === null
    || meta.version !== expectedVersion || meta.size !== expectedSize) { return false; }
  const cachePath: string = CacheConstants.getCacheFilePath(path);
  try {
    await fs.copyFile(cachePath, destPath);                            // 拷贝失败（缓存被删/损坏）→ false
    return true;
  } catch (error) {
    hilog.warn(DOMAIN, TAG, 'readCacheToFile copy failed (miss): %{public}s', error?.message);
    return false;
  }
}
```

要点：
- **force_refresh 消费语义与 `readToFile` 分支对齐**（`CacheStorage.ets:135-137`）：命中前提里先判 miss，命中路径上不再触碰标志；判 miss 时就地清除，保证"一次性标志"不泄漏（下拉刷新 → 必下载；下次保存不受影响）
- meta 比对在前、文件操作在后：纯内存比对零成本，miss 早退
- 与"设置-清理缓存"并发安全：meta 先被删 → 比对 miss；cache 先被删 → copyFile 失败 → false → 走下载

#### P3.3 DatabaseLoad.loadKdbxFileToFile 改造（DatabaseLoad.ets:176-194）

```ts
async loadKdbxFileToFile(request: LoadDatabase, destPath: string,
  onProgress?: TransferProgressCallback): Promise<FileInfo> {
  if (!request.filePath) { ...现状不变... }
  const fileManager: KdbxFileManager = new KdbxFileManager(request.storageType, request.storageConfig);

  // ★ 快速路径候选：存储版本可信 + 缓存元数据存在（纯本地 fs 判定，零网络）
  const fastCandidate: boolean = fileManager.supportsVersionFastPath()
    && CacheMetaService.readMeta(request.filePath) !== null;

  // ★ 候选时守卫强制 getInfo 拿远端 version（不传 precheckSize）；
  //   非候选保持现状优化（precheckSize 已知则跳过 getInfo）
  const guard: GuardCheckResult = await DatabaseLoadGuard.checkBeforeRead(fileManager,
    request.filePath, fastCandidate ? undefined : request.precheckSize);
  if (guard.rejectReason !== null) { throw new Error(guard.rejectReason); }

  // ★ 版本预检快速路径（镜像 DatabaseSave.ets:96-111）
  let fileInfo: FileInfo | undefined = undefined;
  const guardInfo: FileInfo | null = guard.fileInfo;
  if (fastCandidate && guardInfo !== null && guardInfo.version !== null && guardInfo.version !== undefined) {
    const hit: boolean = await fileManager.readCacheToFile(request.filePath, destPath,
      guardInfo.version, guardInfo.size);
    if (hit) {
      fileInfo = guardInfo;      // 远端事实作为基线（version/modifiedTime/size）
      hilog.info(DOMAIN, TAG, 'load fast-path: hit (version matched, skip download)');
      this.postMessage('load_file_success');
    } else {
      hilog.info(DOMAIN, TAG, 'load fast-path: miss (version=%{public}s)', guardInfo.version);
    }
  }

  if (fileInfo === undefined) {
    // miss：现状全量下载（P2 起顺带回填缓存 + meta）
    fileInfo = await fileManager.readToFile(request.filePath, destPath, onProgress);
    this.postMessage('load_file_success');
  }
  return fileInfo;
}
```

要点：
- **precheckSize 让位的取舍**：候选时强制 getInfo 多用 1 次元数据请求（现状该请求被调度缓存优化跳过），换来跳过全量 GET——对大库净收益显著（11.8MB@1.8MB/s 省约 6.5s，换 1 次 PROPFIND）。非候选路径零变化
- **守卫职责不变**：CP1（大小上限）/ CP-DISK（磁盘余量）用 getInfo 到的 `guardInfo.size` 照常判定；候选强制 getInfo 后 `precheckSize` 语义自然由 guardInfo 覆盖
- **命中后的下游不变**：解密管线（`Kdbx.loadFromFile(T0)`）、`sha256HexFile(T0)` 冲突基线实算（D2）、`SuccessMessage` 三元组组装（`DatabaseLoad.ets:89-94,130-131`）全部照旧——命中时 T0 内容即远端内容，实算哈希天然一致
- **进度条语义不变**：命中时无 PROGRESS 事件，`ProgressThrottler.finish()` 现有"全程无事件则无操作"语义（`DatabaseLoad.ets:54-59`）避免假 100%；UI 弹框从 `downloading` 文案短暂停留后进入 `validating`
- 可选打磨（不强制，不阻塞验收）：`'downloading'` 文案（`DatabaseLoad.ets:40`）挪到 miss 分支内，命中时跳过下载文案

### P4 保存链路 meta 回写

| 项 | 内容 |
|---|---|
| 文件 | `CacheStorage.ets`（`writeFromFile`，现 :160-185） |

## 5. 语义保持矩阵

| 场景 | 现状行为 | 改造后行为 | 一致性 |
|------|---------|-----------|--------|
| 正常解锁 + 远端未变 + 缓存在 | 全量 GET 下载 | **PROPFIND + 本地拷贝，跳过下载**（目标行为） | 改变（即本设计目标） |
| 正常解锁 + 远端已变 | 全量下载 | miss → 全量下载 + 回填缓存/meta | 语义等价 |
| 下拉刷新 / 冲突重载（`force_refresh`） | 清标志 + 强制远端 | `readCacheToFile` 判 miss 并就地清标志 → 强制远端；标志不泄漏 | ✓ |
| 仅缓存模式（`only_use_cache`） | `readToFile` 直接读缓存 | `readCacheToFile` 返回 false 让位，`readToFile` 仅缓存分支照旧 | ✓ |
| 关闭本地缓存开关 | 装饰器透明 | `readCacheToFile` 直接 false，全链路透明 | ✓ |
| LOCAL 存储 | 不经 CacheStorage | `BaseFileStorage` 默认 false → 天然 miss | ✓ |
| 离线 + 无缓存 | 下载失败报错 | 候选时守卫 getInfo 失败 → guard fail-open 放行 → `readCacheToFile` 因 guardInfo 为 null 不触发 → `readToFile` 报错（同现状错误语义） | ✓ |
| 同步 / Worker 模式 | — | 共享层逻辑，行为一致 | ✓ |

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| WebDAV 弱 ETag + 秒级 mtime 误判"未变" | **加载侧比保存侧严重：静默打开旧数据**（保存侧误判只导致条件写冲突，可重试恢复） | ① version+size 双比对：KDBX 每次保存整体重加密+压缩，尺寸几乎必变，误判需"同秒内两次修改且压缩尺寸恰好相同"；② 密码库单用户编辑，同秒双写需两设备同时保存；③ kp2a 用 mtime+size 同款方案为先例；④ 兜底入口：下拉刷新 `force_refresh` 必下载 |
| P0 点亮后保存侧快速路径联动激活 | 保存不再全量下载算哈希，冲突检测从"内容哈希终判"变为"版本预检 + 写前复核 + 重试" | 属能力协商的既定语义（`DatabaseSave.ets:96-111` 注释已声明），keeweb 同款；条件写 `checkVersionUnchanged` 收窄 TOCTOU，`VERSION_CONFLICT` 有界重试兜底；**列入回归必测项** |
| 缓存损坏被快速路径服务（磁盘坏块等） | 解密失败报错（v4 header HMAC / v3 header hash），用户看到明确错误而非静默错数据；且 sha256 基线在下次保存暴露不一致 → 版本预检不匹配 → 走下载合并，**不丢数据** | 无需额外校验（D2）；错误文案可后续优化为"缓存损坏，已重新下载"并自动重试一次（可选项） |
| 写缓存成功、写 meta 失败（P2/P4 原子性间隙） | meta 残留旧版本 → 下次比对 miss → 重新下载覆盖。方向安全，仅损失一次机会 | 接受；meta 原子写（tmp+rename）把窗口压到极小 |
| meta 与缓存内容错配（极端竞态：读 meta 后缓存被并发删除） | copyFile 失败 → false → 走下载 | 已由 copyFile try/catch 覆盖 |
| 磁盘占用 | meta <200B/文件；P2 回填使缓存与远端同步覆盖写，不新增副本 | 可忽略 |

### 对设计的两处实施偏离（已记录）

1. **force_refresh 判定前置到守卫之前**（`DatabaseLoad.loadKdbxFileToFile`）：设计中 flag 由 `readCacheToFile` 判 miss 时消费；实际链路里守卫的 `getInfo`（`CacheStorage.getInfo`）会先就地消费该一次性标志，导致主线程模式下 `readCacheToFile` 看到的是已消费的 false → 下拉刷新会错误命中缓存。**故候选条件增加 `!CacheConstants.getForceRefresh()`**，`readCacheToFile` 内的 force 分支保留为纵深防御。
2. **`CacheStorage` 回填失败不影响返回**：回填（缓存 + meta）统一走 `refreshCache`，best-effort 日志告警，与主链路解耦；`write()` 整缓冲路径按设计不写 meta（保存后下次打开 miss → 重新下载，方向安全）。
